# 확인이 필요한 결정 — 2026-08-31

애드센스 재신청 준비와 회원 기능 작업을 하면서 **운영자 확인 없이 판단해서 정한 것들**이다.
읽고 다르면 말해달라. 각 항목에 되돌리는 방법을 적어뒀다.

작업 배경 — 2026-08-30 애드센스 반려. 사유는 두 가지였다.
`게시자 콘텐츠가 없는 화면에 Google 게재 광고` / `가치가 별로 없는 콘텐츠`

---

## 1. 광고 스크립트를 승인까지 뺐다

`web/index.html` 의 `adsbygoogle.js` 를 주석 처리했다. `<meta name="google-adsense-account">` 는 소유권 확인용이라 남겼다.

**왜** — 수동 광고 슬롯(`<ins class="adsbygoogle">`)이 코드 전체에 0개다. 즉 자동 광고를 쓰고 있었고, 사이트 HTML 이 빈 `<div id="root">` 뿐이라 **컨텐츠가 없는 화면에 광고가 삽입되던 상태**였다. 반려 사유 ① 이 정확히 이것이다. 심사 중에 이 상태가 유지되면 다시 걸린다.

**되돌리려면** — 승인 후 `web/index.html` 의 주석을 해제한다. 그때는 자동 광고 대신 **컨텐츠가 있는 자리에만 수동 슬롯**을 두는 편이 안전하다.

---

## 2. 정책 페이지 — 안 주신 값 세 가지를 정했다

| 항목 | 정한 값 | 이유 |
|---|---|---|
| 문의 이메일 구분 | 일반·제휴·저작권 나누지 않고 `newfly101@naver.com` 하나 | 개인 운영이라 창구를 나눌 실익이 없다 |
| 이용약관 시행일 | 2026년 1월 1일 (개인정보처리방침과 동일) | 따로 정할 근거가 없었다 |
| 문의 응답 기간 | "평균 3일 이내 답변을 목표로 합니다" | 확정 약속이 아니라 목표라는 뉘앙스로 적었다 |

**되돌리려면** — `web/src/domains/policy/mobile/` 의 상수(`EFFECTIVE_DATE` 등)만 바꾸면 된다.

### 수집 항목은 코드와 대조해서 정정했다

처음 알려주신 4개(이메일 · 별명 · 프로필 사진 · 연령대)에 **두 가지를 추가**했다. 방침에 적은 것과 실제 저장하는 것이 다르면 그 자체가 문제가 되기 때문이다.

- **네이버 회원 식별자(`providerId`)** — 계정 구분용으로 저장하고 있다
- **자동 수집** — 마지막 로그인 일시, 가입·수정 일시
- **쿠키 3종** — 인증(`ACCESS_TOKEN`) · GA4 분석 · 애드센스 광고

광고 쿠키 항목은 애드센스 심사에서 특히 보는 부분이라 맞춤광고 해제 링크까지 넣었다.

## 3. 내 정보 수정 — 닉네임 하나만 고칠 수 있게 했다

**왜** — 네이버가 준 값(이메일 · 프로필 이미지 · 연령대)을 사이트에서 고쳐봐야 **다음 로그인 때 덮어써진다.** 고칠 수 있는 것처럼 보여주면 혼란만 생긴다. 조회만 되게 했다.

닉네임은 **중복을 허용**한다. DB(`site_users.service_nickname`)에 UNIQUE 제약이 없고, 지금 거는 건 스키마 변경이라 범위를 넘는다. 길이 20자 제한만 검증한다.

**되돌리려면** — 중복을 막으려면 DB 에 UNIQUE 인덱스를 추가하고 서버에 중복 검사를 넣어야 한다. 기존 380명 중 중복 닉네임이 있는지 먼저 확인이 필요하다.

## 4. 탈퇴 — 소프트 삭제 + 1개월 내 재로그인하면 복구

`user_status` 를 `WITHDRAWN` 으로 바꾸고 레코드는 남긴다. 개인정보처리방침에 "탈퇴 후 1개월 보관" 이라고 명시했으니 이 방식이어야 맞다.

**1개월 안에 다시 네이버로 로그인하면 계정이 `ACTIVE` 로 복구된다.**

**왜 복구를 넣었나** — `site_users` 에 `UNIQUE KEY uk_oauth (oauth_provider, oauth_provider_id)` 가 있다. 탈퇴한 계정으로 다시 로그인하면 **새 레코드를 만들 수 없다.** 그대로 두면 탈퇴한 사람이 아무 일 없었다는 듯 로그인되거나, INSERT 가 실패한다. 복구가 가장 자연스러운 처리다.

`BLOCKED` · `SUSPENDED` 는 복구 대상에서 뺐다. 차단당한 계정이 탈퇴로 우회하지 못하게 하기 위해서다.

<!-- 확인 필요 -->
**남은 구멍** — DB 는 복구되는데 **사용자에게 "계정이 복구되었습니다" 를 알려주지 못한다.** 로그인 콜백이 리다이렉트 방식이라 응답에 필드를 실을 수 없어서다. 탈퇴했던 사람이 로그인하면 그냥 들어와져서 "탈퇴가 안 됐나?" 하고 혼란스러울 수 있다.
→ 후속 작업으로 로그인 콜백에 복구 여부를 실어 안내 화면을 띄우는 것을 권한다.

### 부수적으로 정한 것

- **탈퇴 시각을 `updated_at` 으로 본다.** 전용 컬럼이 없다. 1개월 계산이 이 값 기준이라, 다른 이유로 `updated_at` 이 갱신되면 보관 기간이 밀린다. 정확히 하려면 `withdrawn_at` 컬럼을 추가해야 한다.
- **1개월 후 실제 파기하는 배치는 만들지 않았다.** 스케줄러와 운영 정책이 더 필요하다. 지금은 데이터가 계속 남는다.

## 5. 이번 범위에서 뺀 것

| 뺀 것 | 이유 |
|---|---|
| 컨텐츠 최종 갱신일 표시 | 원본 데이터(`data/odds`, `data/players`)에 날짜 필드가 없다. **확률공시 원문 기준일**과 **선수 데이터 수집일** 두 날짜를 주시면 바로 넣는다 |
| `/events/:id` 상세 화면 | 라우트가 없어 죽은 링크였다. 이벤트는 외부 링크형으로 설계됐고 상세 화면이 기획된 적이 없어, 링크를 거는 대신 **링크가 없는 카드**로 바꿨다 |
| 1개월 경과 계정 파기 배치 | 위 4번 참조 |
| favicon `.ico` / `.png` | SVG 만 만들었다. 래스터 이미지는 생성할 수 없다 |

## 6. 아직 답을 기다리는 것

- **확률 공시에 해설을 붙일 것인가** — 지금 JSON 은 공식 고시의 문구·수치를 구조화해 옮긴 것에 가깝다. 저작권보다 **「가치가 별로 없는 콘텐츠」 판정** 쪽 위험이 있다. 붙이면 심사에 유리하지만 갱신마다 글을 써야 한다.
- **로그인 요구 정책** — 확률공시·선수백과는 메뉴에 `loginRequired` 가 있는데 라우트 가드가 없어 실제로는 누구나 들어온다. 가드를 제대로 걸면 **크롤러도 막혀 주력 컨텐츠가 색인되지 않는다.** 보안과 수익화가 정면으로 부딪히는 자리다.
- **커뮤니티 동결 해제** — v1 `posts` 에 글 **242건**이 그대로 있다. 지금 크롤 가능한 상세가 공지 6 + 확률공시 61 = 67개인데, 커뮤니티를 열면 242개가 더 생긴다. 「콘텐츠 부족」 반려였다면 가장 큰 지렛대다. 다만 **쓰기 API 인증 결함을 먼저 막아야 한다.**

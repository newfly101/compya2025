## 1. 배경

`test-docs/cpb2015_1_3.html`(게임 확률 공시)에는 표 안에서 더 상세한 확률표로 나가는

- 43개 문서 · 488개 시트 · 총 1,932,683행 · 디스크 약 766MB

### 3-7. 헤더를 못 찾은 2장 — 상세 조사

기준값(5장)보다 적게 나왔다. 둘 다 표가 없는 게 아니라 **실제 열 이름이 2개뿐이라
"셀 3개 이상"이라는 헤더 판정 기준에 못 미친 케이스**다. 파싱 실패나 안내 페이지가
아니라 데이터 자체가 2열짜리 나열형이라는 뜻.

**문서20 `선수/코치 고유능력 리스트` 中 시트 `코치 고유능력`** (168행, 4열)
- 실제 내용: 안내 문구 2줄("국가대표 전용 고유능력은 국가대표 코치에만 등장합니다" 등)
  다음에 `종류 | 고유능력 이름` 2열 헤더, 그 아래 데이터
- 데이터 예시 3행: 일반\|상위 타선 정확 / 일반\|상위 타선 파워 / 일반\|상위 타선 선구
- 정체: 코치가 가질 수 있는 고유능력 이름을 종류(일반/국가대표 전용/마스터코치 전용)별로
  나열한 참고용 목록. 확률이나 등급 값이 없는 순수 이름 목록이라 열이 2개뿐이다.

**문서33 `전체 레전드 재료 선수 리스트` 中 시트 `재료 리스트`** (411행, 4열)
- 실제 내용: `레전드 이름 | 레전드 재료 선수` 2열. 레전드 이름은 그룹 첫 행에만 나오고
  (예: "이승엽"), 나머지 재료 카드들은 그 아래로 이름 칸이 빈 채 이어진다
- 데이터 예시 3행: (이승엽, 일반 심정수'03) / (빈칸, 일반 박병호'15) / (빈칸, 일반 양준혁'02)
- 정체: 레전드 카드 제작에 쓸 수 있는 재료 카드 목록. 엑셀에서는 세로 병합 셀(레전드
  이름을 여러 행에 걸쳐 병합)이었을 것으로 보이는데, "웹페이지로 저장" 과정에서 병합
  정보가 사라지고 첫 행에만 값이 남는 형태로 바뀐 것으로 보인다.

두 경우 다 파싱 실패가 아니라 **원래부터 확률/등급 없이 이름만 나열한 참고 페이지**다.
사람이 최종 스키마를 정할 때 이 2장은 "확률표"가 아니라 "참고 목록"으로 다르게 다뤄야
한다.

## 5. 사람이 결정해야 하는 것

발견한 사실을 근거로 선택지만 제시한다. 임의로 정하지 않았다.

### 5-1. 문서(no 1~19)에 이름이 없다 — 어떻게 라벨을 붙일까

no 1~19는 원본 문서에서 "[바로가기 - N]"이라는 번호만 있고 설명 문구가 없다(나머지
20~43번은 "FA 확률표", "스카우트권 확률표"처럼 이름이 있음). 실제 내용은 시트 라벨을
봐야 알 수 있다(예: 문서1 = 일반/레어 선수·타자·투수팩, 문서13 = 다른 시즌/카드군).

- **선택지 A**: 시트 라벨 규칙(`{종류} {포지션}팩{번호}`)에서 문서 단위 이름을 역추출해
  붙인다 — 예: 문서1 첫 시트가 "일반 선수팩1"이면 문서 이름을 "일반/레어 선수팩류"로.
  근거: 시트 라벨은 일관된 패턴이라 자동 추출 가능해 보임(§2 표준형 헤더 패턴 참고).
- **선택지 B**: 번호만 유지하고 화면에서는 안 보여준다(내부 식별자로만 사용).
  근거: 게임사가 원래도 번호로만 안내했다 — 억지로 이름을 붙이면 원본과 안 맞을 수 있음.

### 5-2. 시트 라벨의 번호(`팩1`, `팩2`…)는 페이지네이션인가, 다른 콘텐츠인가

문서1 시트 목록을 보면 "일반 선수팩1"~"일반 선수팩8"이 각각 5,004 / 5,004 / … / 1,343행이다.
**5,004라는 숫자가 여러 시트·여러 문서에서 반복된다** — Excel/웹저장 도구의 행 수
제한(예: 5,000행 근처)에 걸려 하나의 논리적 표가 여러 시트로 쪼개졌을 가능성이 높다.

- **선택지 A**: 같은 접두어("일반 선수팩")를 가진 시트들을 이어 붙여 하나의 논리적 표로
  합친다. 근거: 마지막 조각(예: 팩8=1,343행)만 5,004에 못 미치는 패턴이 반복됨 — 전형적인
  "다 채우고 남은 만큼만 있는 마지막 페이지" 모양.
- **선택지 B**: 시트 단위를 그대로 유지한다(합치지 않음). 근거: 정말 페이지 분할인지,
  아니면 실제로 8개의 서로 다른 하위 팩(가중치가 다른 별도 상품)인지는 데이터만으로는
  확정할 수 없음 — 게임사 원본 기획 확인이 필요.

### 5-3. 표준형 469장을 단일 테이블로 합칠 때, 출처 구분 키를 뭘로 할까

같은 선수 이름이 여러 문서·시트에 다른 확률로 등장한다(예: 같은 선수가 "일반 선수팩"과
"올스타 스카우트권"에 서로 다른 확률로 존재). 단순히 `선수명`만으로는 조인이 안 된다.

- **선택지 A**: `(문서no, 시트파일명)` 조합을 그대로 출처 키로 쓴다. 근거: `manifest.json`에
  이미 있는 값이라 추가 가공이 필요 없고, 어떤 문서/시트에서 왔는지 100% 추적 가능.
- **선택지 B**: `(팩 카테고리, 등급)` 처럼 의미 있는 이름으로 정규화한 키를 새로 만든다.
  근거: 화면·API에 노출할 때 `sheet014` 같은 내부 파일명보다 "SSG 구단선택팩"처럼 읽히는
  값이 나음 — 단, §5-1에서 문서 이름을 못 붙인 no 1~19는 이 방식이 어려움.

### 5-4. 예외 19장(§3) — 표준형과 같은 테이블에 넣을까, 따로 뺄까

19장은 컬럼 구성이 제각각이다(확률 없는 4열, 2단 헤더 조합표, 매트릭스, 이름 목록 등).

- **선택지 A**: 표준형 5컬럼 스키마에 억지로 맞추지 않고 예외 19장은 시트별 개별 스키마로
  따로 저장한다. 근거: §3에서 보듯 컬럼 의미 자체가 다른 표들이라(예: 등급 매트릭스 vs
  카드 목록) 억지로 합치면 정보 손실이 생김.
- **선택지 B**: §3-1(구단선택 확정팩, 5장)만 표준형에 `확률=100%`를 채워 합류시키고,
  나머지 14장은 개별 처리한다. 근거: 이 5장은 컬럼 4개가 표준형과 완전히 같고 값이
  결정적(100%)이라 손실 없이 합칠 수 있음.

### 5-5. 헤더 못 찾은 2장(§3-7) — 확률 공시 성격이 맞는가

두 시트 다 확률/등급 정보가 없는 "이름 나열"이다. 확률 공시라는 문서 목적과는 결이
다르다(참고용 콘텐츠 목록에 가까움).

- **선택지 A**: 확률 데이터 파이프라인에서 제외하고 별도 "참고 콘텐츠 목록"으로 다룬다.
  근거: 확률 값이 아예 없어 확률 표시 화면에 넣을 방법이 없음.
- **선택지 B**: 그래도 원본 43개 링크 중 일부이므로 데이터는 전부 받아두되(이미 받음),
  노출 여부만 화면 단에서 결정한다. 근거: 취득 스크립트를 문서별로 분기하지 않는 게
  더 단순함 — 안 보여주는 것과 안 받는 것은 다른 결정.

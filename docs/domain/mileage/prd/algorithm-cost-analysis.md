# 마일리지 저격 경로 — 사전계산 전환 비용 분석

원본: `test-docs/레전드 재료 앱 디자인/design_handoff_mileage/mileage-sniper.html`
측정 방법: 알고리즘 순수계산부를 Node.js로 그대로 옮겨 실행. 브라우저가 아니라 Node 실측치이며, 저사양 모바일 추정은 실측치에 배수를 곱해 표시했다.

## 결론 요약

**권고: 빌드타임 사전계산 + 목표별 정적 파일(정책+기대비용, 개당 1KB 이하).**

- 목표 하나당 계산 62ms가 저사양에서 최대 310ms까지 늘어나는데, 정책 변경 없이 화면을 만질 때마다(현재 위치 select만 바꿔도) 매번 다시 돈다 — 사전계산은 이 부담을 통째로 없앤다.
- 373개 전체를 합쳐도 27KB(gzip)에 불과하고, 포지션 12배가 붙어도 330KB(gzip) 수준이라 서버 인프라 없이 정적 파일만으로 충분하다.
- `teams` 테이블을 만들지 않는다는 확정 사항과도 맞는다 — 서버 API 방식은 별도 서버 연산 경로가 필요해지지만, 정적 파일 방식은 지금처럼 FE 상수(TEAMS_RAW)를 빌드 스크립트가 읽어 파일만 만들면 끝난다.

| 대조 상태 | 손계산/README 값 | 이식 후 계산값 | 결과 |
|---|---|---|---|
| (삼성,2008) → 두산 2008 | 228.6 | 228.6 | 통과 |
| (키움,2015) → 두산 2008 | ≈1,314 | 1,314.3 | 통과 |

로직 변경 없이 이식됐다고 판단. (부가 확인: 유효 목표 수도 373으로 README와 일치)

## 2. 전수 계산 실측 (373개 목표 전부)

| 측정 항목 | 값 |
|---|---|
| 유효 목표 수 | 373 (실측 일치) |
| 목표당 유효 격자 칸 수 | 평균 439 / 최대 439 (모든 목표가 동일 — 유효 칸 여부는 목표와 무관하게 팀·연도 데이터로만 결정됨) |
| 전수 계산 총 소요 시간 | 23.03초 (373개, Node) |
| 목표 1개 계산 시간 | 평균 61.7ms (Node) |
| 저사양 모바일 추정(3~5배) | 185~309ms |

README가 명시한 "브라우저 100~200ms"와 대체로 겹치는 범위다. 단, 이 계산은 **목표 선택뿐 아니라 현재 위치 select를 바꿀 때도 매번 재실행**된다(`render()`가 그때마다 `solve(goalT,goalY)` 호출) — 목표가 그대로인데도 같은 결과를 다시 60ms 들여 계산하는 구조라, 상호작용이 늘수록 체감 비용이 누적된다.

## 3. 사전계산 산출물 크기 실측

3가지 방식 모두 실제 파일로 써서 측정 (373개 목표 기준).

| 방식 | 내용 | 총 raw 크기 | 총 gzip 크기 |
|---|---|---|---|
| A. 정책만 | 칸당 2bit(구단/연도/도착), 373개 합본 | 41,030 B (40KB) | 3,140 B (3.1KB) |
| B. 정책+기대비용 | 정책 2bit + 비용 uint16, 373개 합본 | 368,524 B (360KB) | 27,471 B (26.8KB) |
| C. 목표별 파일 분리 | B와 동일 내용, 목표당 파일 1개 (유저는 1개만 받음) | 개당 988 B (고정) | 개당 평균 208 B (최소171~최대231) |

C는 목표마다 유효 칸 수가 항상 439개로 동일해서 파일 크기가 고정된다. 유저가 실제로 받는 건 이 988B(또는 gzip 208B) 파일 1개뿐이다.

## 4. 포지션 12배 확장 시 추정

README §8 우선순위1(포지션별 행렬)이 들어오면 목표 수가 최대 12배(373→4,476)가 된다. 3단계 수치에 12를 곱해 추정.

| 방식 | raw (×12) | gzip (×12, 선형 추정) | 비고 |
|---|---|---|---|
| A. 정책만 합본 | 492,360 B (481KB) | 37,680 B (36.8KB) | 동일 구조 반복 시 gzip 최선치는 33.5KB까지도 나옴 |
| B. 정책+비용 합본 | 4,422,288 B (4.3MB) | 329,652 B (322KB) | 동일 구조 반복 시 gzip 최선치 320KB |
| C. 목표별 개별 파일 | 파일당 988 B는 불변, 파일 수만 4,476개로 증가 | 파일당 gzip 208B 불변 | 유저 다운로드량은 영향 없음 |

**판정: 셋 다 12배에서도 충분히 견딘다.** B 합본조차 4.3MB(gzip 322KB)로 이미지 몇 장 수준이고, 유저가 실제로 받는 단위는 C 기준 여전히 1KB 미만이라 포지션 확장은 크기 관점에서 문제가 되지 않는다. 다만 373→4,476개 목표 각각을 빌드 시 계산해야 하므로 빌드 시간은 12배(≈4.6분 추정, §6 참고)로 늘어난다 — 이는 CI 빌드 스텝 비용이지 런타임 비용이 아니다.

## 5. 방식 비교 (실측 기반)

| 방식 | 서버 비용 | 클라이언트 부담 | 전송량(목표 1개) | 데이터 변경 시 | 첫 렌더 지연 |
|---|---|---|---|---|---|
| 지금 (FE 실시간 계산) | 없음 | 62ms(Node)/185~309ms(저사양 추정), **상호작용마다 재계산** | 0 (네트워크 요청 없음, TEAMS_RAW가 번들에 내장) | 즉시 (다음 배포부터 자동 반영) | 100~200ms (README 실측) |
| 서버 API 계산 | 요청당 약 62ms 연산 + 별도 서버/엔드포인트 신설 필요 | 0ms (계산은 서버가 함) | 요청당 약 1KB(B포맷) + 네트워크 RTT | 즉시 (다음 요청부터 자동) | 서버 연산(62ms) + 네트워크 RTT(가변, 통상 수십~수백ms) |
| 빌드타임 사전계산 + 정적 파일 | 빌드 시 1회 23초(373개)/약 4.6분(4,476개 추정), 런타임 서버 비용 0 | 0ms (파일 파싱만) | 약 1KB(raw)/0.2KB(gzip), CDN 캐시 가능 | 재빌드 필요(23초~4.6분, 자동화 가능) | 정적 파일 fetch(캐시 시 수십ms) |

**하나로 정하면: 빌드타임 사전계산 + 정적 파일(목표별 분리, B포맷).** 이유 — (1) 상호작용마다 반복되는 60ms대 연산을 저사양 클라이언트에서 완전히 제거하고, (2) 전송량이 1KB 이하로 작아 서버 API의 인프라 비용 없이도 CDN만으로 충분하며, (3) `teams` 테이블을 만들지 않는다는 확정 사항 아래에서 지금과 동일하게 FE 상수(TEAMS_RAW)를 원천으로 두고 빌드 스크립트만 추가하면 되므로 전환 비용이 가장 낮다.

## 6. React 전환 시 분리 지침

지금 UI를 React로 옮길 때, 나중에 사전계산으로 갈아탈 여지를 남기려면:

1. `solve(goalT, goalY)` 호출부를 컴포넌트/훅 한 곳으로 모아라 — 나중에 이 한 곳만 "정적 파일 fetch"로 바꾸면 된다.
2. 반환값 모양(`{V, pol}` 또는 목표별 정책+비용)을 지금과 동일한 인터페이스로 유지해라 — 소비하는 렌더 코드가 실시간 계산인지 정적 파일인지 몰라야 한다.
3. `TEAMS_RAW`는 지금처럼 FE 상수 단일 파일로 유지하고, 사전계산 빌드 스크립트는 이 파일을 import해서 산출물만 만들게 해라 — 원본이 두 곳으로 갈라지면 안 된다.
4. 목표 변경과 무관한 재계산(현재 위치 select 변경 시 재실행되는 문제, §2 참고)은 React 전환 시 `useMemo(goalT, goalY)`로 캐싱해두면 사전계산 전환 없이도 즉시 개선된다.
5. 계산 로직(`sniper-core.mjs`에 옮긴 범위)은 컴포넌트 트리 밖의 순수 모듈로 유지해라 — Node 빌드 스크립트와 브라우저 런타임이 같은 모듈을 그대로 공유할 수 있어야 나중에 전환이 코드 복제 없이 가능하다.

## 이 문서가 풀려는 문제

지금 이 서비스는 **유저가 무엇을 했는지 DB에 전혀 남지 않는다.**

- 행동이 남을 수 있는 테이블(게시글·댓글·좋아요·신고)은 전부 존재하지만 운영 데이터가 **0건**
- 방문 기록은 `AccessLogFilter`가 애플리케이션 로그 파일에 `log.info`로만 찍고 DB에 안 넣음
- 퀴즈는 제출 API 자체가 없고, 트래픽 상위 컨텐츠(레전드 재료·히스토리 모드·확률공시)는 전부 비로그인 조회 전용

그래서 "3일 연속 방문", "댓글 10개 작성" 같은 걸 **걸 자리가 없다**. 업적을 만들려면 판정할 사실이 있어야 하는데 그 사실이 없다.

이 문서는 그 사실을 쌓는 **바닥 한 층**만 설계한다. 이 층이 생기면 그 위에 무엇을 얹을지는 나중에 정해도 된다.

### 설계를 지배하는 숫자 하나

| 구분 | 값 |
|---|---|
| GA 기준 활성 사용자 | 약 4,100명 |
| 가입 회원 | 438명 (그중 최근 활성 146명) |
| 평균 체류 | 2분 02초 |

**활성 사용자 30명 중 1명 정도만 로그인 회원이다.** 이 비율이 아래 § 1~§ 2의 거의 모든 판단을 결정한다.

## § 1. 무엇을 기록할 것인가

### 1.1 기록 대상

| 이벤트 | 발생 위치 | 로그인 필요 | 기록 가치 | 어뷰징 취약도 |
|---|---|---|---|---|
| 로그인 성공 | `AuthController.naverCallback` | 필요 | **상** — 연속 출석의 유일한 근거 | 낮음 (네이버 왕복 필요) |
| 하루 첫 접속 | `UserController` 내 `/api/users/me` (앱 부팅 시 `AuthProvider`가 호출) | 필요 | **상** — 로그인 세션이 유지되면 재로그인이 안 일어나므로, 출석은 이쪽으로 세야 정확 | 중 → 하루 1회 제약으로 무해화 |
| 닉네임 최초 설정 | `UserController.updateMe` | 필요 | 중 — 계정 완성도 지표, 온보딩 유도용 | 낮음 (1회성) |
| 댓글 작성 | `CommentController` | 필요 | **상** — 남는 산출물이 있는 행동 | 중 (도배 가능) |
| 게시글 작성 | `PostController` 쓰기 | 필요 | **상** | 중 |
| 게시글·댓글 좋아요/싫어요 | `PostReactionController`, `CommentReactionController` | 필요 | 중 — 되돌릴 수 있어 "횟수"로 세면 안 됨 | **상** (토글 반복) |
| 신고 | `ReportController` | 필요 | 하 — 운영 지표로는 필요, **보상에 연결 금지** | **상** (허위 신고 유인) |
| 퀴즈 제출 | **현재 없음** — 신규 API 필요 | 필요(로 설계 권고) | **상** — 트래픽 상위 컨텐츠에 붙는 유일한 참여 행동 | 중 |
| 컨텐츠 상세 열람(레전드 재료 등) | `FunPlayerLegendController` 등 | 현재 불필요 | 하 | 상 (새로고침만으로 발생) |

**지금 당장 실제로 이벤트가 발생하는 것은 위 표의 위쪽 3개(로그인·하루 첫 접속·닉네임 설정)뿐이다.**
댓글·좋아요는 서버 API가 완성돼 있으나 모바일 화면이 mock 데이터라 서버에 도달하지 않고, 퀴즈 제출은 API 자체가 없다.

→ 그래서 § 7의 도입 순서는 **로그인·출석 2종만으로 먼저 완결**되게 짜여 있다. 컨텐츠 결정이 늦어져도 기록 레이어는 오늘부터 굴러간다.

### 1.2 비로그인 사용자의 행동도 기록할 것인가 — **기록하지 않는다**

| 근거 | 설명 |
|---|---|
| 계정에 붙일 수 없다 | 활성 4,100명 중 로그인은 146명. 나머지 97%의 행동 기록은 **어떤 계정에도 귀속되지 않는 행** — 업적·연속출석·등급 어디에도 쓸 수 없다. 이 레이어의 존재 이유가 "계정별 사실 축적"인데 목적과 안 맞는다 |
| 이미 GA가 하고 있다 | 비로그인 집단의 행동은 **집계로만 의미가 있고**, 그건 이미 GA4(`G-KCC3QTZWZW`)와 GTM이 수집 중이다. 인기 페이지 순위·체류시간이 그 산출물이다. DB에 같은 걸 또 쌓는 건 중복 |
| 식별자를 새로 만들어야 한다 | 비로그인을 세려면 브라우저 식별 쿠키를 새로 심어야 한다. 개인정보 수집 항목이 늘고, 정확도는 GA보다 나쁘다 |
| 나중에 이어붙일 수 없다 | 익명 식별자로 쌓은 기록을 로그인 시점에 계정으로 병합하는 건 가능은 하지만, 병합 규칙·중복 계정 문제로 복잡도가 급증한다. 438명 규모에 맞는 비용이 아니다 |

**대신 이렇게 한다** — 비로그인 사용자가 로그인 필요 행동을 시도하다 막힌 순간(로그인 유도 노출·클릭)은 **GA 커스텀 이벤트로만** 남긴다. `web/src/infra/analytics/ga.js`의 `pushEvent`가 이미 있으므로 신규 인프라가 필요 없다. 이건 "전환 퍼널 분석"이지 "활동 기록"이 아니다.

### 1.3 기록하지 **않을** 것

| 대상 | 기록하지 않는 이유 |
|---|---|
| 페이지 조회 전량 | ① 양 — 활성 4,100명이 평균 2분 체류하며 여러 화면을 본다. 조회를 전부 남기면 월 수십만 행이 되는데, 그 대가로 얻는 건 GA가 이미 주는 것과 같다. ② 봇 오염 — 빌드마다 `web/scripts/prerender.mjs`가 puppeteer로 주요 라우트를 방문하고, AdSense 크롤러도 돈다. 우리 배포 파이프라인이 스스로 만든 조회가 섞여 신뢰할 수 없다. ③ 개인정보 — "누가 언제 무엇을 봤는지"는 열람 이력이라 보관·파기 의무가 붙는데, 얻는 값이 그 부담을 정당화하지 못한다 |
| 스크롤·클릭 같은 화면 조작 | 업적으로 만들 수 있는 사실이 아니고, 자동화로 무한 생성 가능 |
| 검색어·필터 조작 | 같은 이유. 필요해지면 GA 이벤트로 충분 |
| 로그아웃 | 계정 상태 변화가 없고, 기록해도 판정에 쓸 곳이 없다 |
| 게시글 조회수 | 이미 `site_post.view_count`가 글 단위로 세고 있다. **유저 단위가 아니라서 이 레이어와 무관** — 그대로 둔다 |

한 줄 원칙: **"유저가 의도를 갖고 한 행동, 그리고 계정에 귀속되는 것만 남긴다."**

## § 2. 저장 구조

### 2.1 원장과 집계를 나눌 것인가 — **나눈다**

| 안 | 내용 | 장점 | 단점 | 판정 |
|---|---|---|---|---|
| 원장만 | 행동이 일어날 때마다 한 줄씩 쌓고, 필요할 때 세어 본다 | 단순. 나중에 규칙이 바뀌어도 다시 계산 가능 | 연속 출석은 "날짜가 이어졌는지"라 세는 걸로 안 나온다. 화면 진입마다 집계 쿼리가 돈다 | X |
| 집계만 | 유저별 카운터만 올린다 | 조회가 가장 빠르고 가볍다 | 어뷰징으로 부풀려진 수치를 되돌릴 수 없다. 업적 조건을 바꾸면 소급 적용 불가. **한 번 잘못 세면 영원히 잘못** | X |
| **둘 다** | 원장에 한 줄 쌓고, 같은 트랜잭션에서 카운터를 갱신 | 조회는 빠르고, 문제가 생기면 원장으로 다시 계산할 수 있다 | 테이블 2~3개, 갱신 코드가 약간 늘어난다 | **채택** |

**"둘 다"를 고르는 근거**는 규모다. 로그인 회원 146명이 하루 몇 건씩 남긴다고 봐도 **연간 수만 행** 수준이라, 원장 유지 비용이 사실상 없다. 반대로 집계를 안 두면 연속 출석 계산과 업적 판정이 매 요청마다 스캔을 돌게 된다. 즉 이 규모에서는 **둘 다 두는 게 가장 싸다.** 양자택일할 상황이 아니다.

### 2.2 테이블 초안 (DDL 수준 · 실제 SQL 파일은 이번 범위 아님)

기존 관례를 따른다 — `site_` 접두(유저 FK가 필요하므로), `BIGINT AUTO_INCREMENT` PK, `DATETIME DEFAULT CURRENT_TIMESTAMP`, `ON DELETE CASCADE`, 컬럼 COMMENT 필수. 파일은 최신 관례대로 테이블 단위 개별 파일(`sql/V3/site/CREATE_TABLE_*.sql`) 권고.

#### (1) 활동 원장 — `site_user_activity`

```sql
CREATE TABLE site_user_activity
(
    id            BIGINT AUTO_INCREMENT PRIMARY KEY               COMMENT 'PK',
    user_id       BIGINT       NOT NULL                           COMMENT 'site_users.id',
    activity_type VARCHAR(40)  NOT NULL                           COMMENT '행동 종류. 예: LOGIN, DAILY_VISIT, COMMENT_WRITE',
    target_type   VARCHAR(30)  NULL                               COMMENT '행동 대상 종류. 예: POST, COMMENT, QUIZ (없으면 NULL)',
    target_id     BIGINT       NULL                               COMMENT '행동 대상 식별자 (없으면 NULL)',
    dedupe_key    VARCHAR(120) NULL                               COMMENT '중복 차단 키. 하루 1회 이벤트는 날짜(2026-09-04), 대상별 1회는 대상 식별자. 제한 없는 이벤트는 NULL',
    occurred_at   DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '행동 발생 시각',
    occurred_date DATE         NOT NULL                           COMMENT '발생 일자 (연속 출석 계산·일일 상한 검사용)',

    UNIQUE KEY uk_activity_dedupe (user_id, activity_type, dedupe_key),
    INDEX idx_activity_user_date (user_id, occurred_date),
    INDEX idx_activity_type_date (activity_type, occurred_date),
    CONSTRAINT fk_activity_user
        FOREIGN KEY (user_id) REFERENCES site_users (id) ON DELETE CASCADE
) ENGINE = InnoDB
  DEFAULT CHARSET = utf8mb4
    COMMENT = '유저 활동 원장 (append-only)';
```

설계 의도 4가지:

- **`dedupe_key` + UNIQUE 가 어뷰징 방어의 1차 방어선이다.** 애플리케이션에서 "이미 했나?"를 확인하고 넣는 방식은 동시 요청 두 개가 동시에 통과할 수 있다. DB 제약이면 뚫리지 않는다. MariaDB는 UNIQUE 안에서 NULL 중복을 허용하므로, **제한 없는 이벤트는 `dedupe_key`를 NULL로 두면 자동으로 제약이 안 걸린다** — 테이블을 나눌 필요가 없다.
- **`activity_type`을 ENUM이 아니라 VARCHAR로 둔다.** 이 프로젝트는 이미 DB ENUM과 자바 enum이 어긋난 사고가 2건 있었다(`tables.md`). 그리고 행동 종류는 컨텐츠를 열 때마다 늘어난다 — ENUM이면 그때마다 DDL 변경이 필요하다. 유효값 검증은 자바 enum이 하고, DB는 문자열만 받는다.
- **`occurred_date`를 따로 둔다.** `occurred_at`에서 날짜를 뽑아 쓰면 인덱스를 못 탄다. 연속 출석과 일일 상한 검사가 전부 날짜 단위라 별도 컬럼이 값어치를 한다.
- **소프트 삭제 컬럼(`is_deleted`)을 두지 않는다.** 백엔드 컨벤션 § 4의 기본 규칙에서 **의도적으로 벗어나는 지점**이며, 이유는 원장이 "일어난 일의 기록"이기 때문이다. 일어난 일은 취소되지 않는다. 좋아요를 껐을 때는 원장을 지우는 게 아니라 아래 § 4.2 방식으로 집계를 다시 계산한다. 매퍼 XML의 `WHERE is_deleted = FALSE` 관례도 이 테이블에는 적용하지 않는다 — 신규 매퍼 작성자가 헷갈리기 쉬운 지점이라 명시한다.

#### (2) 활동 집계 — `site_user_activity_stat`

```sql
CREATE TABLE site_user_activity_stat
(
    user_id       BIGINT      NOT NULL                           COMMENT 'site_users.id',
    activity_type VARCHAR(40) NOT NULL                           COMMENT '행동 종류',
    total_count   INT         NOT NULL DEFAULT 0                 COMMENT '누적 횟수 (원장으로 언제든 재계산 가능)',
    first_at      DATETIME    NULL                               COMMENT '최초 발생 시각',
    last_at       DATETIME    NULL                               COMMENT '최근 발생 시각',
    updated_at    DATETIME    NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '갱신 시각',

    PRIMARY KEY (user_id, activity_type),
    CONSTRAINT fk_activity_stat_user
        FOREIGN KEY (user_id) REFERENCES site_users (id) ON DELETE CASCADE
) ENGINE = InnoDB
  DEFAULT CHARSET = utf8mb4
    COMMENT = '유저별 행동 누적 집계 (원장에서 파생 — 원본 아님)';
```

- PK를 `(user_id, activity_type)` 복합으로 잡아 `INSERT ... ON DUPLICATE KEY UPDATE` 한 방으로 갱신한다. 별도 AUTO_INCREMENT PK를 두지 않는 것이 이 테이블의 유일한 관례 이탈이며, 이유는 **행 자체가 "이 유저의 이 행동" 하나로 유일**하기 때문이다.
- 이 테이블은 **원본이 아니라 파생**이다. 값이 이상하면 지우고 원장에서 다시 만들면 된다. 코드 주석과 컬럼 COMMENT에 이 성격을 반드시 남긴다.

#### (3) 출석 스트릭 — `site_user_streak`

```sql
CREATE TABLE site_user_streak
(
    user_id         BIGINT   NOT NULL PRIMARY KEY               COMMENT 'site_users.id',
    current_streak  INT      NOT NULL DEFAULT 0                 COMMENT '현재 연속 출석 일수',
    best_streak     INT      NOT NULL DEFAULT 0                 COMMENT '역대 최고 연속 출석 일수',
    total_days      INT      NOT NULL DEFAULT 0                 COMMENT '누적 출석 일수 (연속 아님)',
    last_visit_date DATE     NULL                               COMMENT '마지막 출석 일자',
    updated_at      DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '갱신 시각',

    CONSTRAINT fk_streak_user
        FOREIGN KEY (user_id) REFERENCES site_users (id) ON DELETE CASCADE
) ENGINE = InnoDB
  DEFAULT CHARSET = utf8mb4
    COMMENT = '유저별 연속 출석 상태 (원장에서 파생)';
```

- 연속 출석을 **`site_users.last_login_at`에 의존하지 않는다.** 그 컬럼은 로그인 시점에만 갱신되는데, 로그인 쿠키가 살아 있으면 매일 접속해도 재로그인이 안 일어나 값이 안 바뀐다. 즉 출석 판정에 쓰면 틀린다. `last_visit_date`를 따로 갖는 이유가 이것이다.
- 갱신 규칙: 오늘 날짜가 `last_visit_date`와 같으면 아무것도 안 함 / 하루 차이면 `current_streak + 1` / 그보다 벌어졌으면 `1`로 리셋. `best_streak`은 `current_streak`과 비교해 큰 값 유지.
- 날짜 기준 시각대는 **`Asia/Seoul` 고정**. 서버 타임존 설정에 의존하지 말고 코드에서 명시한다(전원 국내 사용자이며, 서버 타임존 설정 실측은 안 했다 — § 8 참고).

### 2.3 site / fun 중 어디에 둘 것인가

`site_` 를 쓴다. 근거는 `site_users` FK가 필요하고, 실측상 `site_` = 운영 콘텐츠 / `fun_` = 게임 콘텐츠 관례가 있기 때문이다. 나중에 `fun_` 쪽 컨텐츠(레전드 카드 등)에 붙는 행동이 생기면 `target_type` / `target_id` 문자열로 가리키고 **DB 레벨 FK는 걸지 않는다** — 두 접두가 물리적으로 같은 스키마인지 확인되지 않았기 때문이다(`_current-state-code.md` § 6.3, 미확인).

## § 3. 적재 방식

### 3.1 어느 계층에서 기록하나 — **서비스 계층에서 이벤트를 발행하고, 별도 소비자가 저장**

| 후보 | 판정 |
|---|---|
| 컨트롤러에서 직접 저장 | X — 기록 코드가 컨트롤러마다 흩어지고, 기록이 실패하면 응답 자체가 깨진다 |
| 인터셉터 (URL 단위) | X — URL만 보고는 "무엇을 했는지"를 못 담는다(대상 식별자를 못 꺼냄). 게다가 `permitAll` 경로가 전부 걸려 § 1.3에서 안 남기기로 한 조회까지 들어온다 |
| 어노테이션(AOP)만으로 | X — 대상 식별자를 어노테이션에서 꺼내려면 SpEL 파싱이 필요하다. 이 팀 규모에 비해 과한 마법이고, 디버깅이 어렵다 |
| **스프링 이벤트 발행 + 트랜잭션 커밋 후 비동기 소비** | **채택** |

동작 순서:

1. 본 기능 서비스가 자기 일을 끝내고 `ApplicationEventPublisher`로 활동 이벤트를 발행한다 (서비스 코드에 추가되는 건 **한 줄**)
2. 소비자는 `@TransactionalEventListener(phase = AFTER_COMMIT)` + `@Async`
3. 소비자가 **새 트랜잭션**(`REQUIRES_NEW`)에서 원장 insert → 집계 upsert → 스트릭 갱신을 한 덩어리로 처리

이 방식을 고르는 이유 3가지:

- **본 기능이 롤백되면 기록도 안 남는다.** 커밋 이후에만 소비자가 돈다. "댓글은 실패했는데 댓글 작성 기록만 남는" 상황이 원천적으로 안 생긴다
- **기록이 실패해도 본 기능이 안 깨진다.** 다른 스레드·다른 트랜잭션이므로 본 요청은 이미 응답을 내보낸 뒤다
- **컨텐츠가 늘어나도 배관을 안 건드린다.** 새 행동이 생기면 이벤트 한 줄 추가 + `activity_type` 상수 하나 추가로 끝난다. 이번 라운드에서 "어떤 컨텐츠를 먼저 열지"를 몰라도 되는 이유가 이것이다

### 3.2 기록 실패가 본 기능을 망가뜨리지 않게 하는 방법

| 장치 | 내용 |
|---|---|
| 예외 삼키기 | 소비자 최상단을 `try/catch (Exception)`로 감싸고 `log.warn`만 남긴다. 기록 실패는 **절대** 위로 전파하지 않는다 |
| 중복 저장 무해화 | `dedupe_key` UNIQUE 위반은 정상 흐름으로 취급한다 — 로그 레벨도 `debug`. 재시도로 같은 이벤트가 두 번 와도 조용히 무시된다 |
| 전용 스레드 풀 | 활동 기록 전용 `ThreadPoolTaskExecutor`를 작게 잡는다(스레드 2, 큐 500 수준). 기본 풀을 쓰면 기록 지연이 다른 비동기 작업을 막는다 |
| 큐 넘침 시 정책 | 큐가 차면 **버리고 경고 로그**. 요청 스레드에서 실행하는 정책(CallerRuns)은 쓰지 않는다 — 기록 때문에 본 요청이 느려지면 안 된다는 원칙과 정면으로 어긋난다 |
| 지표 복구 | 버려지거나 실패한 기록이 있어도 집계는 원장에서 다시 만들 수 있다(§ 2.1). 스트릭도 원장의 `occurred_date`만 있으면 재계산 가능 |

### 3.3 기존 인증 배관 재사용

- 인증 필터(`JwtAuthFilter`)가 매 요청 쿠키를 검증해 `request.setAttribute("userId", userId)`를 심는다. **이게 전 도메인 공통 진입점이고, 이미 로그인 필요 컨트롤러 전부가 이 값을 쓴다.**
- 활동 기록도 **새 배관을 만들지 않고 이 값을 그대로 쓴다.** 컨트롤러가 `userId`를 꺼내 서비스에 넘기고, 서비스가 이벤트에 담아 발행한다 — 현재 코드의 파라미터 전달 패턴을 그대로 따르므로 서비스 계층이 `HttpServletRequest`를 알 필요가 없다.
- 인증 채널이 HttpOnly 쿠키 단일(`Authorization` 헤더 차단)이라, 기록 이벤트에 담기는 `userId`는 **서버가 검증한 값**이다. 클라이언트가 보낸 유저 식별자를 믿는 구간이 없다 — 이건 지금 구조의 장점이므로 깨뜨리지 않는다.
- 세션이 STATELESS라 서버에 붙잡아 둘 상태가 없다. 그래서 "하루 첫 접속"을 세션 시작으로 판정할 수 없고, **날짜 기반 `dedupe_key`가 세션의 역할을 대신한다.**

## § 4. 어뷰징 방지

### 4.1 무엇을 막는가

| 공격 | 방어 |
|---|---|
| 새로고침 반복 | 하루 1회 이벤트는 `dedupe_key = 발생일자` → **DB UNIQUE가 막는다**. 두 번째부터는 조용히 무시 |
| 같은 대상 반복 | 대상별 1회 이벤트는 `dedupe_key = 대상 식별자` → 같은 글에 좋아요를 백 번 눌러도 원장 1행 |
| 이중 클릭·재시도 중복 | 위 두 제약이 그대로 커버. 애플리케이션 사전 확인 방식과 달리 동시 요청에도 안 뚫린다 |
| 도배(댓글을 초당 여러 개) | 행동별 **하루 상한**을 둔다. 원장에 `(user_id, occurred_date)` 인덱스가 있어 오늘치 카운트가 싸다. 상한 초과분은 원장에는 남기되 **집계·보상에서 제외** — 그래야 나중에 상한을 조정해도 재계산이 가능하다 |
| 자동화 스크립트 | 진입 장벽이 이미 높다 — 네이버 OAuth 통과 필요 + HttpOnly 쿠키 단일 채널이라 토큰을 스크립트가 꺼내 쓰기 어렵다. 그 위에 하루 상한과 **이상치 리포트**(하루 상한에 근접·도달한 계정 목록을 관리자에게 노출)만 얹는다. 캡차는 146명 규모에 과하다 |
| 다중 계정 | 네이버 계정을 여러 개 만들면 가능. 완전 차단은 불가능하며, **보상 설계 단계에서 "계정을 늘려도 이득이 적은 보상"을 고르는 것으로 대응**한다(이번 범위 밖, 다음 라운드 입력으로 남김) |

### 4.2 토글형 행동(좋아요)의 처리

좋아요는 켰다 껐다 할 수 있어 "횟수"로 세면 무한 증식한다. 그래서:

- 원장에는 `dedupe_key = 대상 식별자`로 **처음 켠 순간만** 남는다 (해제해도 원장은 그대로)
- 집계 `total_count`는 "좋아요를 누른 **고유 대상 수**"로 정의한다 — 즉 원장 행 수와 같다
- 해제 이벤트는 **원장에 남기지 않는다.** 남겨봐야 판정에 못 쓰고, 켜고 끄기를 반복하면 원장만 부푼다

### 4.3 어뷰징에 강한 이벤트 / 약한 이벤트 구분 기준

판별 질문 4개. **"예"가 많을수록 약한 이벤트**다.

1. 사용자가 혼자서, 남의 협조 없이 반복할 수 있는가?
2. 되돌릴 수 있는가? (되돌릴 수 있으면 되돌리고 다시 하기로 카운트를 올릴 수 있다)
3. 결과물이 아무도 안 보는가? (남에게 보이는 산출물이 남으면 함부로 못 한다)
4. 외부 시스템 왕복 없이 발생하는가? (네이버 로그인 같은 왕복은 자동화 비용이 크다)

| 분류 | 이벤트 | 보상 연결 |
|---|---|---|
| **강함** | 로그인 성공, 하루 첫 접속, 닉네임 최초 설정 | 그대로 연결 가능 |
| **중간** | 댓글 작성, 게시글 작성, 퀴즈 제출 | 하루 상한을 둔 뒤 연결 |
| **약함** | 좋아요/싫어요 | 고유 대상 수로만, 낮은 가중치로 연결 |
| **연결 금지** | 신고, 싫어요 단독, 컨텐츠 열람 | 기록은 하되 **보상에 절대 연결하지 않는다** — 신고에 보상을 걸면 허위 신고를 사는 셈이다 |

## § 5. 개인정보와 보관

### 5.1 현재 고지 상태 (실측)

개인정보처리방침 화면(`web/src/domains/policy/mobile/PrivacyPolicyScreen.jsx`)은 이미 자동 수집 항목으로 **"접속 IP, 쿠키, 방문 일시, 서비스 이용 기록, 브라우저 및 기기 정보"** 를 고지하고 있고, 탈퇴 시 보관 기간을 **1개월**로 명시한다.

→ 이 문서가 설계한 활동 기록은 **"서비스 이용 기록"이라는 이미 고지된 항목의 범위 안**에 들어간다고 판단한다. 다만 보관 기간과 이용 목적(업적·보상 산정)이 지금 문안에 없어 **문안 보강은 필요**하다. 신규 동의 절차가 필요한지는 법적 판단 영역이라 아래 마커로 뺐다.

### 5.2 무엇을 담고 무엇을 안 담는가

| 항목 | 결정 |
|---|---|
| 접속 IP | **원장에 담지 않는다.** IP는 이미 `AccessLogFilter`가 애플리케이션 로그에 남기고 있어 중복이고, DB에 개인 식별성이 높은 값을 새로 축적할 이유가 없다. 어뷰징 조사가 실제로 필요해지면 그때 앱 로그와 대조한다 |
| User-Agent · 기기 정보 | 담지 않는다. 업적 판정에 쓰지 않는다 |
| 행동 대상(글·댓글 식별자) | 담는다. 다만 **내용은 담지 않고 식별자만** 담는다 — 원문이 지워지면 기록에서도 사라지게 하기 위함 |
| 유저 식별자 | 담는다. 이 레이어의 존재 이유 |

### 5.3 보관 기간

| 데이터 | 보관 | 이유 |
|---|---|---|
| 활동 원장 | **12개월 롤링 삭제** (권고) | 연속 출석·업적 재계산에 필요한 최소 기간. 1년이면 연간 단위 업적까지 커버되고, 그 이상 과거를 다시 계산할 일은 사실상 없다 |
| 활동 집계 · 스트릭 | 계정이 살아 있는 동안 유지 | 개인 식별성이 낮은 숫자만 남고(누적 횟수·연속 일수), 업적의 근거라 지우면 유저가 가진 것이 사라진다 |
| 탈퇴 계정의 전부 | 계정 파기 시점에 함께 파기 | 아래 § 5.4 |

### 5.4 탈퇴 정책과의 정합

기확정: **탈퇴 = 소프트 삭제(`user_status = WITHDRAWN`) + 1개월 내 재로그인 시 복구.**

여기에 활동 기록을 맞추면:

- 탈퇴 즉시 활동 기록을 지우면 **복구했을 때 업적·연속출석이 사라진다** → 복구 정책이 무의미해진다
- 그래서 **탈퇴 시 활동 기록도 그대로 둔다.** 화면에서 안 보이면 되고, 그건 계정 상태로 이미 걸러진다
- 1개월이 지나 계정을 실제로 파기할 때 활동 기록도 같이 파기한다. 테이블 FK가 전부 `ON DELETE CASCADE`라 계정 행을 지우면 자동으로 딸려 삭제된다

⚠️ **다만 그 파기 배치가 지금 없다.** 코드 주석(`UserServiceImpl`)에 "보관 기간 경과 — 재활성화 대상 아님. WITHDRAWN 유지 (삭제 배치 대상, 이번 범위 아님)"이라고 적혀 있다. 즉 **방침은 1개월 후 파기라고 고지했는데 실제 파기는 아무도 안 하고 있다.** 이건 활동 기록과 무관하게 이미 존재하는 격차이며, 활동 기록을 도입하면 그 격차 위에 데이터가 더 쌓인다.

### 5.5 사용자 결정이 필요한 지점

**[사용자 결정 필요] ① 개인정보처리방침 문안 보강 범위**
- 선택지 A: 기존 "서비스 이용 기록" 항목 안에 포함된 것으로 보고, 이용 목적(업적·보상 산정)과 보관 기간(12개월)만 문안에 추가
- 선택지 B: "활동 이력"을 별도 수집 항목으로 신설하고 재동의를 받음
- **권고: A.** 이미 고지된 항목의 구체화이지 새 항목의 신설이 아니라고 보는 게 자연스럽다. 다만 최종 판단은 법무 영역이라 개발이 단독 결정할 사안이 아니다

**[사용자 결정 필요] ② 활동 원장 보관 기간**
- 선택지 A: 12개월 후 삭제 / 선택지 B: 무기한 보관
- **권고: A(12개월).** 무기한은 방침의 "목적 달성 후 지체 없이 파기"와 충돌하고, 12개월이면 재계산에 필요한 범위를 덮는다. 원장을 지워도 집계·스트릭은 남으므로 유저가 잃는 것은 없다

**[사용자 결정 필요] ③ 탈퇴 1개월 경과 계정 파기 배치를 이번에 만들 것인가**
- 선택지 A: 활동 기록 도입과 함께 파기 배치도 만든다 / 선택지 B: 기존 격차를 그대로 두고 별도 과제로 미룬다
- **권고: A.** 이미 방침에 1개월 파기를 고지해 놓은 상태라 격차가 있고, 활동 기록이 쌓이면 그 격차가 더 커진다. 다만 이건 운영 트랙 작업이라 이번 설계의 후속으로 분리해 잡는 게 맞다

## § 6. 광고 차등 노출 연동 — 요구사항만

> ⚠️ 광고 삽입 코드는 **다른 세션이 진행 중**이다. 이 절은 광고를 어떻게 넣을지가 아니라, **기록·인증 레이어가 무엇을 제공해야 하는가**만 적는다.
>
> 기확정: 로그인 유저 보상은 **전면광고 면제만**. 배너·인피드는 로그인 여부와 무관하게 유지.

### 이미 있는 것 (새로 만들 필요 없음)

- 앱이 뜰 때 `AuthProvider`가 `/api/users/me`를 호출하고, 결과가 Redux `auth` 상태(`user` / `userRole` / `initialized`)에 들어간다
- 따라서 **"로그인했는가"는 `auth.user !== null`로 이미 알 수 있다.** 광고 쪽에서 쓸 신규 API는 필요 없다

### 광고 쪽에 넘겨야 할 요구사항 3가지

| # | 요구사항 | 왜 |
|---|---|---|
| 1 | 전면광고 노출 판정은 **`auth.initialized === true` 이후에만** 한다 | 앱이 뜬 직후 `/api/users/me` 응답이 오기 전까지는 로그인 여부를 모르는 구간이 있다. 그 구간에 판정하면 **로그인 유저에게도 전면광고가 뜬다**. "모르면 안 띄운다"가 기본값이어야 한다 |
| 2 | 전면광고 마크업은 **빌드 스냅샷에 들어가면 안 된다** | `web/scripts/prerender.mjs`가 빌드마다 puppeteer로 주요 라우트를 방문해 렌더된 DOM을 `dist/{route}/index.html`로 저장한다. **이 방문에는 쿠키가 없어 항상 비로그인 상태로 스냅샷된다.** 전면광고가 그 HTML에 박히면 로그인 유저도 그 마크업을 먼저 받는다. 클라이언트 마운트 이후에만 삽입해야 한다 |
| 3 | 전면광고 노출·면제 결과는 **GA 이벤트로만** 남긴다 | § 1.3 원칙(광고 노출은 유저의 의도적 행동이 아님). DB 원장에 넣지 않는다. `pushEvent`(`web/src/infra/analytics/ga.js`)를 그대로 쓰면 된다 |

### 알아 둘 한계

- 전면광고를 띄우는 주체가 브라우저라, **서버가 면제를 강제할 수단이 없다.** 마음먹으면 우회 가능하다. 다만 우회해서 얻는 게 "광고를 덜 본다"뿐이라 방어할 가치가 없다 — 별도 대책을 만들지 않는다
- 광고 자체가 현재 **애드센스 승인 전까지 비활성 상태**(2026-08-31 반려 이력, 스크립트 비활성 커밋 있음)다. 즉 이 보상은 **광고가 다시 켜져야 의미가 생기는 조건부 보상**이다. 활동 기록 레이어는 광고 승인 여부와 무관하게 먼저 가도 된다

## § 7. 도입 순서

각 단계는 **그 단계만 끝나도 쓸모가 생기게** 잘랐다. 다음 단계가 늦어져도 앞 단계가 헛일이 되지 않는다.

### 첫째 — 원장 하나와 배관, 그리고 행동 두 개

- 만드는 것: `site_user_activity` 테이블 / 이벤트 발행·소비 배관(§ 3) / 기록 지점은 **로그인 성공 + 하루 첫 접속** 2종만
- **끝나면 가능해지는 것: 오늘부터 회원의 출석이 DB에 쌓이기 시작한다.** 어떤 참여형 컨텐츠도 필요 없고, 컨텐츠 결정을 기다릴 이유가 사라진다

### 둘째 — 집계와 스트릭, 그리고 내 활동 조회

- 만드는 것: `site_user_activity_stat` · `site_user_streak` / 소비자에서의 갱신 로직 / 원장에서 다시 계산하는 재계산 기능 / `GET /api/users/me/activity` 조회 API
- **끝나면 가능해지는 것: "○일 연속 방문 중"을 화면에 띄울 수 있고, 업적 판정이 스캔 없이 한 번의 조회로 끝난다**

### 셋째 — 기록 지점 확장

- 만드는 것: 컨텐츠가 열리는 대로 이벤트 발행 한 줄씩 추가. 현실적 선행 조건이 각각 있다 — 댓글·좋아요는 커뮤니티 모바일 화면의 서버 연결이 먼저, 퀴즈는 제출 API 신설이 먼저
- **끝나면 가능해지는 것: 새 컨텐츠를 열 때마다 기록 레이어를 다시 설계할 필요가 없어진다. 어떤 컨텐츠를 먼저 여느냐가 이 층의 구조를 바꾸지 못하게 된다**

### 넷째 — 상한과 파기

- 만드는 것: 행동별 하루 상한 / 이상치 계정 리포트 / 원장 12개월 롤링 삭제 배치 / (결정되면) 탈퇴 계정 파기 배치
- **끝나면 가능해지는 것: 보상(업적·등급)을 실제로 걸어도 부정 축적과 개인정보 축적 양쪽이 안전해진다**

> **업적 정의·포인트·등급 테이블은 여기에 없다.** 이번 범위가 아니고, 위 넷째까지 끝난 뒤 별도 라운드에서 설계한다. 다만 이 설계는 그 위층이 `site_user_activity_stat` / `site_user_streak` 두 테이블만 읽으면 판정이 되도록 모양을 맞춰 뒀다.

## § 8. 자체 평가

### 이 설계가 틀렸을 수 있는 지점

| 지점 | 어떻게 틀릴 수 있나 | 완화책 |
|---|---|---|
| 비로그인을 DB에 기록하지 않기로 한 것 | 나중에 "비로그인 → 로그인 전환 퍼널"을 DB로 정밀 분석하고 싶어지면 **소급이 안 된다**. 안 쌓은 과거는 못 만든다 | 같은 이벤트를 GA에 남겨 두면 집계 수준으로는 부분 대체된다. 그래도 개인 단위 추적은 영영 불가 |
| 활동 유형을 문자열로 둔 것 | 오타로 잘못된 값이 들어가면 DB가 안 막아 준다 | 자바 enum으로만 발행하게 강제하고, 관리자 화면에 "알 수 없는 활동 유형" 목록을 노출해 조기 발견 |
| 집계를 실시간 갱신하는 것 | 기록량이 크게 늘면 집계 행에 쓰기 경합이 생긴다 | 현재 규모(로그인 146명)에서는 나타나지 않는다. 로그인 회원이 10배 넘게 늘면 집계를 주기적 배치로 돌리는 방식으로 바꿔야 한다 |
| "하루 첫 접속"을 `/api/users/me` 호출로 세는 것 | 이 호출은 앱이 뜰 때마다 나가는데, 쿠키가 만료되면 안 나갈 수도 있다. 반대로 탭을 여러 번 열면 여러 번 나간다(중복은 `dedupe_key`가 막음) | 날짜 기준 중복 차단이 있어 과다 집계는 안 생긴다. 과소 집계(접속했는데 안 세짐) 가능성은 남아 있으며, 실제 데이터를 한 달 본 뒤 로그인 이벤트 수와 대조해 검증할 것 |
| 원장을 append-only로 두고 소프트 삭제를 안 넣은 것 | 백엔드 컨벤션의 기본 규칙에서 벗어난다. 새 개발자가 관례대로 `WHERE is_deleted = FALSE`를 넣으면 쿼리가 깨진다 | 테이블 COMMENT와 매퍼 XML 상단 주석에 명시. § 2.2에도 적어 뒀다 |

### 확인하지 못한 것

| 항목 | 상태 |
|---|---|
| 회원 수 실측 불일치 | 코드 실측 문서는 `site_users` **123행**(2026-08-20 스냅샷), 기존 결정 문서는 **380명**, 이번 브리프는 **438명**이라고 한다. 세 값이 서로 다르다. 어느 쪽이든 소규모라 설계는 안 바뀌지만, **집계 방식·상한 수치를 정하기 전에 실제 행 수를 한 번 확인해야 한다** |
| 서버·DB 타임존 설정 | 미확인. 그래서 § 2.2에서 날짜 계산을 `Asia/Seoul`로 코드에 고정하라고 적었다. 서버 설정에 의존하면 배포 환경이 바뀔 때 연속 출석이 하루씩 어긋난다 |
| `site_` 와 `fun_` 이 같은 스키마인지 | 미확인(코드 실측 § 6.3에서도 미확인). 그래서 `fun_` 대상에는 FK를 걸지 않는 설계로 회피했다 |
| `last_login_at` 실제 갱신 코드 | 미확인. 이 설계는 그 컬럼에 의존하지 않으므로 결론이 바뀌지 않는다 |
| 애드센스 수동 슬롯이 화면에 실제로 삽입됐는지 | 미확인. § 6은 요구사항만 적어 영향 없음 |
| 퀴즈 정답 채점이 어디서 이뤄지는지 | 미확인. 그래서 퀴즈를 "제출 API 신설이 선행 조건"으로만 적고 설계에 넣지 않았다 |

### 가정한 것

- **활동량 규모 가정** — 로그인 회원 146명 × 하루 몇 건 = 연간 수만 행. 이 가정 위에서 "원장을 그냥 다 남겨도 된다"는 결론이 나왔다. 로그인 회원이 수천 명 단위로 늘면 원장 보관·인덱스 전략을 다시 봐야 한다
- **행동 유형이 앞으로 늘어난다는 가정** — 그래서 활동 유형을 ENUM이 아닌 문자열로 두고, 기록 지점 추가가 DDL 변경을 요구하지 않게 했다
- **참여형 컨텐츠 결정이 늦어질 수 있다는 가정** — 그래서 첫 단계를 로그인·출석만으로 완결시켰다. 이 가정이 틀려서 컨텐츠가 먼저 정해지더라도, 순서만 바뀔 뿐 구조는 그대로 쓸 수 있다

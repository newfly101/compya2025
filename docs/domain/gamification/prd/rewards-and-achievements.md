# 게이미피케이션 — 보상과 업적 설계

> 작성일 2026-09-04. 대상: 컴프야펀 모바일 웹. 저장구조·API 설계는 범위 밖(별도 담당) — 여기서는 **무엇을 업적으로 만들고 무엇으로 보상할지**만 정한다.

---

## § 1. 이 서비스에서 게이미피케이션이 풀어야 할 문제

정보사이트라 트래픽의 96%가 비로그인이고, 대부분 "검색으로 들어와 정보 하나 보고 2분 만에 나간다." 이 구조에서 게이미피케이션이 손댈 수 있는 지점은 두 군데뿐이다.

| 문제 | 대상 | 성공 측정 |
|---|---|---|
| 비로그인 유입을 가입시키기 | GA 신규 3.2천 / 활성 4.1천 | 로그인(네이버) 전환 이벤트 발생 수, 비로그인 세션 대비 가입 전환율 추이 |
| 가입한 438명을 다시 오게 하기 | 최근 활성 146명 (438명 중 33%) | `site_users.last_login_at` 기준 최근 7일·30일 내 재로그인 비율의 증가 |

두 문제는 해법이 다르다. 첫 번째는 "가입하면 뭐가 좋은지"가 로그인 시점 이전에 보여야 하고, 두 번째는 "가입한 사람이 왜 또 와야 하는지"가 로그인 이후에 쌓여야 한다. 아래 설계는 이 두 갈래를 따로 다룬다.

⚠️ GA 커스텀 이벤트 종류가 이번 조사에서 상세 확인되지 않았다. 위 지표가 실제로 수집 가능한지는 별도 확인 필요 (§8).

## § 2. 보상으로 줄 수 있는 것 — 재고 조사

게임이 아니라 팬사이트이므로 현금성·게임 재화성 보상(포인트를 현금처럼 쓰거나 아이템으로 바꾸는 것)은 애초에 배제한다. 실제로 줄 수 있는 것만 남긴다.

| 보상 | 유저 체감 | 운영 비용 | 남용 위험 | 지금 가능한가 |
|---|---|---|---|---|
| 전면광고 면제 (확정) | 중 — 광고 짜증을 없애는 실질적 이득 | 낮음 — 로그인 여부만 확인하면 됨 | 낮음 | 가능. 단 현재 애드센스 광고 자체가 승인 대기로 꺼져 있어 **광고가 다시 켜져야 체감이 생긴다** |
| 칭호·뱃지 | 낮음~중 — 수집욕은 자극하지만 보여줄 화면이 없음 | 낮음 — 정적 목록 + 달성 여부 플래그만 | 낮음 | 가능. 단 지금 마이페이지가 백지 상태라 뱃지를 "어디서 보여줄지"부터 없다 |
| 명예 표시 (가입 N개월째, 총 방문일수 등) | 낮음 — 은근한 소속감 정도 | 매우 낮음 | 없음 | 가능 |
| 프로필 꾸미기 (테두리·배경색 등) | 낮음 — 커뮤니티가 동결 상태라 남에게 보여줄 자리가 없음 | 중 — 이미지 에셋 제작 필요 | 낮음 | 지금은 의미 없음. 보여줄 곳이 생긴 뒤(커뮤니티 재개 등)에나 유효 |
| 기능 해금 (시뮬레이터 저장 슬롯 확대 등) | 중 — 실사용자에겐 실질적 | 중 — 기능 자체를 새로 만들어야 함 | 낮음 | 애매. 시뮬레이터는 재작업 보류 상태라 지금 얹을 대상이 아님 |
| 쿠폰·이벤트 우선 알림 | 중 — 트래픽 1위 카테고리라 유인력 있음 | 중 — 알림 발송 인프라 자체가 없음(신설 필요) | 낮음 | 지금 불가. 알림 인프라부터 필요 |

결론: 지금 바로 쓸 수 있는 보상은 **전면광고 면제(확정) + 명예 표시 + 칭호·뱃지** 세 가지뿐이다. 뱃지·칭호도 진열장(마이페이지)이 없으면 반쪽짜리라는 점은 §8에 남긴다.

## § 3. 업적 카탈로그

### 3.1 설계 원칙

- 지금 트래픽이 실제로 몰리는 곳(백과사전·투수/타자 스킬·히스토리 모드 레전드 재료·스킬 시뮬레이터)에서 나오는 업적을 우선한다.
- **단순 조회 수 업적은 만들지 않는다.** "선수 페이지 10회 열람" 같은 조건은 새로고침 반복이나 탭 여러 개로 순식간에 채워진다. 대신 "서로 다른 항목을 몇 개 봤는가"(중복 제거 집계)로 조건을 건다 — 새로고침을 아무리 해도 같은 선수를 다시 보는 것은 집계에 안 잡히게 한다.
- 참여형 콘텐츠(댓글·좋아요·퀴즈 제출)는 아직 실제로 작동하지 않는 기능이다 (커뮤니티 FE 미연결, 퀴즈 제출 API 자체가 없음). 이 라운드에서는 "만약 열리면" 식으로 남발하지 않고, 지금 만들 수 있는 것만 정식 항목으로 두고 나머지는 조건부로만 짧게 남긴다.

### 3.2 초기 도입분 (지금 있는 것만으로 가능)

| 업적 | 달성 조건 | 어느 행동에 붙는가 | 어뷰징 취약도 | 도입 난이도 |
|---|---|---|---|---|
| 가입 환영 | 네이버 로그인 최초 1회 성공 | 로그인 | 없음 | 하 |
| 내 이름 정하기 | 서비스 닉네임 최초 설정 | 닉네임 변경(1회성) | 없음 | 하 |
| 3일 연속 출석 | 하루 1회 이상 로그인이 3일 연속 | 로그인 | 낮음 | 중 (스트릭 계산 로직 필요) |
| 7일 연속 출석 | 동일, 7일 | 로그인 | 낮음 | 중 |
| 한 달 개근 | 동일, 30일 | 로그인 | 낮음 | 중 |
| 다시 만나서 반가워 | 가입 후 30일 이상 지나 재로그인 | 로그인 | 낮음 | 하 |
| 백과사전 탐구자 | 서로 다른 선수 상세를 10명 이상 열람 (일자별 distinct 집계) | 선수 백과사전 상세 조회 | 낮음 — 같은 선수 반복 열람은 집계 안 됨 | 중 (신규 조회 이벤트 필요) |
| 투수 마스터 | 서로 다른 투수 스킬 상세를 10개 이상 열람 | 투수 스킬 조회 | 낮음 | 중 |
| 타자 마스터 | 서로 다른 타자 스킬 상세를 10개 이상 열람 | 타자 스킬 조회 | 낮음 | 중 |
| 레전드 재료 수집가 | 히스토리 모드 레전드 재료 세트 중 1개를 전부 열람 | 레전드 재료 탐색 | 낮음 | 중 |
| 조합의 달인 | 스킬 시뮬레이터에서 서로 다른 조합을 5회 이상 실행 (조합 값이 같으면 재실행 미집계) | 스킬 시뮬레이터 실행 | 중 — 조합을 미세하게 바꿔가며 반복하는 것까지는 막기 어려움, 다만 "같은 조합 재실행"만 막아도 새로고침 어뷰징은 차단됨 | 중상 (조합 식별 로직 필요) |
| 쿠폰 챙기기 | 쿠폰 코드 복사/사용 버튼 클릭 5회 (단순 목록 조회가 아니라 클릭 행동) | 쿠폰 상세 행동 | 낮음 | 중 (신규 클릭 이벤트 필요) |

12개, 전부 지금 존재하는 화면·행동을 기반으로 하되 조회 이벤트 자체는 신규로 붙여야 한다 (§3.4).

### 3.3 나중 도입분 (조건부 — 선행 조건이 먼저 풀려야 함)

이 항목들은 아직 없는 기능을 전제로 하므로 **지금 확정하지 않는다.** 선행 조건과 함께만 남긴다.

| 업적(가칭) | 선행 조건 | 어뷰징 취약도 |
|---|---|---|
| 첫 댓글 / 좋아요 활동 | 커뮤니티 FE-BE 연결 완료 (지금 mock 데이터, 서버 미연결) | 높음 — 스팸 댓글/좋아요 반복, rate limit 별도 필요 |
| 퀴즈 정답 이력 | 퀴즈 정답 제출 API 자체가 없음(신규 설계 필요) | 낮음 — 정답이 하나뿐이라 정답 공유 가능성은 있음 |

이 두 항목은 참여형 콘텐츠를 무엇부터 열지 결정된 뒤 다시 설계한다.

### 3.4 기록 레이어에 요구하는 것 (요구사항만, 설계 아님)

- 로그인 성공 이벤트 — 일자별 distinct 기록 (스트릭 계산용, `last_login_at` 단일 값으론 연속일수 계산 불가)
- 닉네임 최초 설정 여부 판별 (현재도 `service_nickname` NULL 여부로 판별 가능해 보임)
- 선수 백과사전 상세 조회 이벤트 — 유저ID + 선수ID + 일자
- 투수/타자 스킬 상세 조회 이벤트 — 유저ID + 스킬ID + 일자
- 히스토리 모드 레전드 재료 세트별 열람 이벤트 — 유저ID + 세트ID + 항목ID
- 스킬 시뮬레이터 실행 이벤트 — 유저ID + 조합 식별값 + 일자 (동일 조합 재실행 판별용)
- 쿠폰 코드 복사/사용 클릭 이벤트 — 유저ID + 쿠폰ID
- 위 조회형 이벤트는 전부 지금 `permitAll`(비로그인 접근 가능) 화면이라, **비로그인 상태의 조회는 기록하지 않고 로그인 유저만 기록**하는 것을 권장 (비로그인 행동을 로그인 후 소급 반영하면 세션 병합 문제 발생)
- (조건부, 나중) 퀴즈 정답 제출 이벤트, 댓글/좋아요 이벤트 — 각각 API·FE 연결이 먼저 필요

## § 4. 연속 출석

- **하루 기준 시각**: 자정(KST 00:00) 리셋. 다만 자정 직후 바로 끊긴 것으로 처리하면 야간 이용자가 억울하게 스트릭을 잃으므로, 자정 후 몇 시간의 유예는 두지 않고 "그날 하루 안에 1회 로그인"만 요건으로 단순하게 둔다.
- **끊겼을 때 처리**: 스트릭은 리셋하되, **누적 총 방문일수는 별도로 계속 쌓아서 사라지지 않게** 한다. 화면에는 "현재 연속 3일" 옆에 "지금까지 총 47일 방문"을 같이 보여줘서, 스트릭이 끊겨도 그동안 쌓은 게 사라지지 않았다는 걸 보여준다.
- **보상 곡선**: 3일 / 7일 / 30일 세 단계만 둔다. 재화가 없으므로 보상은 뱃지 + (광고 재활성화 이후) 전면광고 면제 기간 같은 명예성 표시 위주로, 단계가 올라갈수록 화려한 표시만 바뀌는 정도로 완만하게 간다.
- **끊기면 이탈하는 역효과 완화**:
  - 스트릭이 끊긴 것을 처벌적으로 보여주지 않는다 ("연속 기록이 초기화되었습니다" 같은 부정적 문구 대신 누적 총 방문일수를 앞세운다).
  - 한 달에 1회 정도 "결석 보호"를 자동 적용해 하루 빠져도 스트릭이 안 끊기게 한다. 규모가 작아 운영 비용은 거의 없다.
  - 리마인더 푸시로 재촉하지 않는다 — 애초에 알림 인프라가 없고, 438명 규모에서 공격적 리마인더는 역효과가 더 크다.

## § 5. 등급·레벨·랭킹 판단

**등급·레벨·공개 랭킹 전부 도입하지 않는다.**

근거:
- 가입 438명, 최근 활성은 146명뿐이라 상위권이 몇 명으로 고정되기 쉽다. 랭킹을 처음 본 유저가 바로 하위권으로 시작하면 "어차피 못 따라간다"는 체념만 남긴다.
- 커뮤니티가 동결 상태라 랭킹을 봐줄 다른 사람 자체가 없다. 랭킹은 남이 볼 때 의미가 생기는데, 지금은 그 "남"이 없다.
- 평균 체류 2분 02초의 정보 사이트다. 세션 목적이 "정보 하나 보고 나가기"로 명확한데, 레벨업 개념이 끼어들 만큼 상호작용이 잦지 않다.
- 대안으로 개인만 보는 지표(내 최고 연속 기록, 내 총 방문일수)만 쓴다 — 남과 비교하지 않는 지표라 위 위험이 없다.

## § 6. 전면광고 면제 정책의 세부

⚠️ 정책 수준만. 구현·코드 설계는 다른 세션이 진행 중이므로 이 문서는 손대지 않는다. ⚠️ 현재 애드센스 광고는 승인 대기로 비활성 상태(2026-08-30 1회 반려 이력)라 아래 정책은 **광고가 다시 켜진 시점부터** 의미가 생긴다.

- 로그인 유저: 전면광고 완전 면제 (확정 사항, 배너·인피드는 그대로 유지).
- 비로그인 유저: 세션당 전면광고 노출은 최대 1회로 제한한다. 평균 체류가 2분에 불과해 두 번째 노출까지 갈 여유가 없다.
- 진입 직후(첫 페이지 로드) 노출은 하지 않는다 — 반려 사유가 "콘텐츠 없는 화면에 광고"였던 만큼, 콘텐츠를 한 번 이상 소비한 뒤(페이지 전환 시점 등)에만 노출한다.
- 같은 방문자에게 너무 자주 뜨지 않도록 최소 재노출 간격(쿨다운)을 둔다.

## § 7. 도입하지 말아야 할 것

| 요소 | 이유 |
|---|---|
| 포인트/재화 시스템 | 교환 가치가 없는 숫자를 쌓게 하는 건 팬사이트에서 게임머니처럼 오해를 살 뿐이고, 실제로 쓸 곳도 없다 |
| 공개 랭킹/리더보드 | §5 사유 그대로 — 모수가 작고 볼 사람이 없다 |
| 다단계 일일 미션/퀘스트 | 평균 체류 2분짜리 정보 소비 세션에 게임식 미션 체크리스트를 끼얹으면 피로감만 준다 |
| 무한 레벨업/경험치 곡선 | 상호작용 빈도 자체가 부족해 숫자만 커지고 체감 보상은 따라오지 않는다 |
| 친구 초대형 미션 | 유입 1위가 네이버 카페(외부 커뮤니티)라 개인 초대 바이럴 구조와 안 맞고, 모수도 작아 실효가 없다 |
| 푸시 알림 기반 리마인더 | 알림 인프라 자체가 없고, 작은 유저 풀에 과도한 리마인더는 이탈을 앞당긴다 |
| 기간제 이벤트 뱃지 남발 | 지속적으로 새 이벤트를 만들어 운영해야 하는 부담이 지금 운영 규모에 안 맞는다 |

## § 8. 자체 평가

- **뱃지·칭호를 보여줄 화면이 없다.** 마이페이지가 현재 백지 상태라, §2에서 "가능하다"고 판단한 보상도 진열장이 생기기 전까지는 체감이 약하다. 이 문서는 마이페이지의 존재를 전제로 진열장 개념을 제안했지만, 화면 설계 자체는 범위 밖이다.
- **§1의 측정 지표가 실제로 수집되는지 불확실하다.** GA 커스텀 이벤트(`infra/analytics/ga.js`)의 상세 종류를 이번 조사에서 확인하지 못했다. 로그인 전환·재방문율을 GA로 볼 수 있다고 전제했지만 검증이 필요하다.
- **연속 출석 계산에 필요한 일자별 로그인 기록이 지금 있는지 불확실하다.** `site_users.last_login_at`은 최종 1건만 저장하는 컬럼으로 보여, 스트릭 계산에는 별도의 일자별 기록이 필요할 수 있다 — 이건 저장구조 담당 몫으로 넘긴다.
- **§6 정책의 발동 시점이 불확실하다.** 광고 재활성화 일정이 정해지지 않아 "언제부터 이 정책이 실제로 작동하는지"는 이 문서로 답할 수 없다.

# 관리자 화면 UI 설계

> 설계 문서. 디자인 시안도 코드도 아니다. "무엇을 어떤 원칙으로 만들 것인가"만 정한다.
> 전제 근거: `admin-current-state.md`(현황 실측), `responsive-foundation.md`(화면 폭 대응 실측).
> 이 문서는 **모바일 화면 기준 재설계**를 다룬다. PC에서도 지금처럼 화면 가운데 좁은 폭으로 보이는 상태를 유지하며, PC 폭 지원(PC 브라우저에서 화면을 넓게 보여주는 것)은 뒤쪽 "나중에 할 것" 구역에 모아 미뤄 두었다.

## 왜 다시 만드는가

- 공용 부품이 없어서 검색창·필터·입력창·로딩/에러 문구를 화면마다 처음부터 다시 썼다. 쿠폰·이벤트·공지 화면이 각각 220~233줄이고, 꾸미는 규칙(스타일 클래스)도 파일마다 30개 안팎씩 따로 있다. **한 곳을 고쳐도 나머지에 반영되지 않는다 — 이게 "매번 개박살"의 정체다.**
- 같은 관리자 화면끼리도 방식이 갈린다. 입력창이 어떤 데선 아래에서 올라오고 어떤 데선 화면 가운데 뜬다. 삭제 확인이 있는 화면과 없는 화면이 섞여 있다.
- 완성 안 된 것이 그대로 남아 있다 — 없는 파일을 불러오는 커뮤니티 관리자 표 2개, 가짜 댓글 데이터, 라우터에 연결 안 된 화면 2개, 아무도 안 쓰는 노출 스위치 부품.
- PC로 열면 화면 가운데 스마트폰 폭(480px) 기둥 하나만 보인다. 관리자 작업을 PC에서 하기 불편하지만, 이번 재설계에서는 이 문제를 바로 풀지 않고 뒤로 미룬다(아래 "나중에 할 것" 참고).

## 설계 원칙

**하나. 관리자 화면 파일에는 UI를 새로 그리지 않는다 — 부품을 불러 쓰기만 한다.**
화면 파일이 하는 일은 "어떤 데이터를 · 어떤 항목으로 · 어떤 필터로 보여줄지"를 부품에 넘기는 것까지다. `<input>`·`<button>`·오버레이를 화면 파일 안에서 직접 꾸미는 것을 금지한다. → 30개씩 중복된 스타일 클래스와 220줄대 화면 파일을 구조적으로 막는다.

**둘. 부품은 나중에 모습이 바뀌더라도 다시 만들지 않아도 되게 짠다.**
이 저장소에는 이미 "모바일용 목록 / PC용 표"로 나눠 만들다 만 파일 세트가 있고, 아무 화면도 그걸 불러 쓰지 않는 고아 코드로 남았다. 지금은 모바일 모습만 만들지만, 부품이 "무엇을 보여줄지"만 정의로 받게 만들어두면 나중에 모습을 추가할 때 부품을 다시 만들지 않는다. → 같은 실패를 반복하지 않는다.

**셋. 같은 동작은 같은 모습으로 한다 — 등록·수정·삭제·노출전환의 표준을 하나로 고정한다.**
삭제는 반드시 확인창을 거친다(브라우저 기본 확인창 `window.confirm` 폐기). 노출 켜기/끄기는 목록에서 바로 되고, 그 부품은 이미 있는 것을 쓴다. → 화면마다 다른 삭제/토글 방식을 없앤다.

**넷. 연결되지 않은 화면과 깨진 참조는 남기지 않는다.**
화면은 주소(라우터)에 연결된 상태로만 완료 처리한다. 없는 파일을 불러오는 코드, 가짜 데이터를 심어둔 화면은 그 화면을 손대는 시점에 반드시 제거한다. → "만들었는데 켜보면 안 뜬다"를 없앤다.

## 만들 부품 목록

| 부품 (파일명 제안) | 하는 일 | 모바일에서 | 쓰이는 곳 | 새로/재사용 |
|---|---|---|---|---|
| 관리자 화면 틀 (`AdminPageFrame`) | 관리자 화면 한 개의 바깥 테두리·좌우 여백·최대 폭을 정함 | 폭 꽉 채움 | 모든 관리자 화면 | 새로 |
| 화면 머리말 (`AdminPageHeader`) | 제목 + 한 줄 설명 + 총 건수 + 주요 버튼(등록) | 세로 쌓기, 등록 버튼은 폭 전체 | 모든 관리자 화면 | 새로 |
| 검색·필터 줄 (`AdminFilterBar`) | 검색창과 필터 칩을 한 묶음으로 배치 | 검색창 한 줄 + 아래 칩 가로 스크롤 | 쿠폰·이벤트·공지·유저 (+위키·커뮤니티 신규 적용) | 새로 |
| 검색창 (`SearchField`) | 글자 입력받아 목록을 걸러냄 | 폭 전체 | 검색·필터 줄 안에서만 | 새로 |
| 필터 칩 묶음 (`FilterChipGroup`) | 여러 개 중 하나 고르는 알약 버튼들 | 가로 스크롤 | 검색·필터 줄 안에서만 | 새로 |
| **목록 (`AdminList`)** | 항목 정의를 받아 카드로 그림 | 카드 세로 나열 | 모든 목록 화면 | 새로 |
| 목록 상태 표시 (`ListStateView`) | 불러오는 중 / 오류 / 결과 없음 화면 | 동일 | 모든 목록 화면 | 새로 |
| **입력 창 (`AdminFormPanel`)** | 등록·수정 입력 폼을 담는 창 | 화면 가운데 뜨는 창 | 등록·수정 있는 모든 화면 | 새로 |
| 확인 창 (`ConfirmDialog`) | "정말 삭제할까요?" 예/아니오 | 화면 가운데 작은 창 | 삭제·비활성화 동작 전부 | 새로 (위키 3곳 중복분 흡수) |
| 버튼 (`Button`) | 주요/보조/위험 3종 버튼 | 세로 쌓임, 폭 전체 | 전 화면 | 새로 |
| 입력 항목 (`Field`) | 라벨 + 글자/**여러 줄**/숫자/날짜/선택/체크 입력 | 라벨 위, 입력 아래 (한 줄에 1개) | 모든 입력 폼 | 새로 |
| 행 동작 묶음 (`RowActions`) | 수정·삭제 버튼 세트 | 카드 아래쪽 가로 배치 | 모든 목록 화면 | 새로 |
| 메뉴 카드 (`AdminMenuCard`) | 하위 관리 화면으로 들어가는 카드 | 세로 1열 | 관리자 홈, 위키 관리 홈 | 새로 (두 곳 통일) |
| 노출 스위치 | 목록에서 바로 켜기/끄기 | 동일 | 쿠폰·이벤트·공지·유저·위키 | **재사용** (`VisibleToggle` — 지금 아무도 안 씀) |
| 상태 배지 3종 | 상태·라벨·고정 표시 | 동일 | 모든 목록 | **재사용** (`LabelBadge`/`PinnedBadge`/`StatusBadge`) |
| 구역 블록 | 제목 + 본문 묶음 | 동일 | 입력 폼 안 항목 그룹 | **재사용** (`SectionBlock`/`SectionHeader`) |

새로 만들 것 **13개**, 이미 있는 것 재사용 **3종(5개 파일)**.

주요 부품 상세:
- **목록 (`AdminList`)** — 이 설계의 중심. 화면은 "어떤 항목을 보여줄지"의 정의만 넘긴다(예: 제목·코드·할인·만료일·노출 여부·동작). 그러면 부품이 정의 순서대로 카드 한 장에 쌓아 그린다. 항목 정의에 "좁을 땐 감춤" 표시를 달 수 있어서, 항목이 8~10개로 많은 게시글 관리 같은 화면도 모바일에서는 핵심 3~4개만 보이게 할 수 있다. 화면이 목록 마크업을 직접 쓰는 일이 사라진다.
- **입력 창 (`AdminFormPanel`)** — 내용(입력 항목들)은 화면 가운데 뜨는 창 안에 담긴다. admin은 운영자 혼자 쓰는 화면이라 아래에서 올라오는 방식 대신 가운데 모달로 통일한다(2026-08-20 결정). 지금 흩어져 있는 바텀시트 3벌 + 중앙 모달 6벌을 전부 이걸로 대체한다.
- **확인 창 (`ConfirmDialog`)** — 위키 3개 화면 파일 맨 아래에 똑같이 복사돼 있는 확인 모달을 하나로 뺀 것. 쿠폰의 브라우저 기본 확인창도 이걸로 바꾼다. 삭제뿐 아니라 "비활성화", "일괄 처리" 확인까지 같은 창을 쓴다.
- **화면 머리말 (`AdminPageHeader`)** — 화면 안에 제목을 또 만들지 않는다. 위쪽 검은 바(글로벌 상단바)는 지금처럼 "← 쿠폰 관리"를 담당하고, 머리말은 그 아래에서 설명·총 건수·등록 버튼만 맡는다. 역할이 겹치지 않게 선을 긋는다.

## 지금 만들되, 나중을 막지 않는 법

지금은 모바일 모습만 만들지만, 나중에 PC 폭을 지원하기로 했을 때 **부품을 다시 만들지 않으려면** 지금 아래 세 가지만 지켜두면 된다. 비용이 거의 안 드는 것만 골랐다.
- **목록 부품은 "무슨 항목을 보여줄지"만 넘겨받아 그리게 만든다.** 화면 파일이 카드 모양을 직접 그리지 않고, 제목·코드·할인 같은 항목 정의만 부품에 건넨다. 나중에 표 모습을 추가할 때 화면 쪽은 안 고쳐도 된다.
- **폭 값을 숫자로 직접 쓰지 말고 이름 붙인 값(변수) 하나를 통해 쓴다.** 예: `480`을 여기저기 박아 쓰지 않고 "공개용 폭"이라는 이름의 값 하나로 참조한다. 나중에 그 값만 바꾸면 관련된 곳이 전부 따라온다.
- **입력 폼을 여닫는 방식과 그 안의 내용을 분리해 둔다.** "화면 가운데 뜨는 창"이라는 여는 방식과 "안에 들어갈 입력 항목들"을 분리해서 만들면, 나중에 여는 방식만(예: 오른쪽에서 밀려나오는 패널로) 바꿔 끼울 수 있다.

| 구분 | 항목 (3개씩) | 이유 |
|---|---|---|
| 지금 안 해도 되는 것 | ① PC용 표 레이아웃 실제 구현 ② 화면 틀에 PC 최대 폭(1280px 등) 값 실제 반영 ③ 여러 개 선택 일괄 처리 동작 실제 구현 | 부품에 자리(항목 정의 방식·이름 붙인 값·선택 칸)만 열어두면, 실제 구현은 나중에 채워도 이미 만든 화면들은 고치지 않아도 된다 |
| 지금 안 하면 나중에 다 뜯어야 하는 것 | ① 목록이 카드 모양을 화면 파일 안에서 직접 그리는 구조 ② 폭 값(480 등)을 화면마다 숫자로 직접 박아 쓰는 것 ③ 입력 폼의 "여는 방식"과 "안의 내용"을 한 덩어리로 묶어 만드는 것 | 나중에 값 하나 바꿔서 될 일이 아니라, 이미 만든 화면 전부를 찾아다니며 다시 써야 하는 일이 된다 |

## 화면 골격 표준

관리자 화면 한 개는 항상 이 순서다: **글로벌 상단바 → 머리말(제목·설명·건수·등록) → 검색·필터 → 목록 → (겹쳐 뜨는) 입력 창 / 확인 창.** 예외를 만들지 않는다.
```
┌──────────────────────────┐
│ ←   쿠폰 관리            │  글로벌 상단바 (이미 있는 것)
├──────────────────────────┤
│ 쿠폰 관리                │  머리말 (설명 · 총 12건)
│ [    + 쿠폰 등록       ] │  폭 전체
│ [ 🔍 제목 또는 코드     ] │  검색창
│ [전체][노출][숨김] →     │  칩 가로 스크롤
├──────────────────────────┤
│ ┌ 카드 ────────────────┐ │
│ │ 여름 할인 쿠폰  [노출]│ │  ← 노출은 눌러서 바로 전환
│ │ SUMMER24 · 10% · 만료 2026-08-31         │
│ │           [수정][삭제]│ │
│ └──────────────────────┘ │
│ (카드 반복)              │
└──────────────────────────┘
   등록/수정 → 화면 가운데 창이 뜸
```

## 어느 것부터 만들 것인가

순서 기준 세 가지: (1) 지금 실제로 켜지는 화면을 먼저, (2) 부품을 가장 넓게 검증할 수 있는 화면을 기준 화면으로, (3) 깨져 있는 것은 부품이 완성된 뒤에 부품으로 대체.

- **먼저 할 것** — 화면은 손대지 않고 부품부터 만든다. 관리자 화면 틀 · 머리말 · 검색필터 줄 · 목록 · 목록 상태 표시 · 입력 창 · 확인 창 · 버튼 · 입력 항목.
- **그다음** — **쿠폰 관리 한 개**를 부품으로 전부 갈아끼운다. 검색·필터·입력창·삭제 확인이 모두 있는 유일한 화면이라 부품 검증에 가장 적합하다. 이 화면이 이후 모든 화면의 기준이 된다.
- **그다음** — 이벤트 관리, 공지 관리. 쿠폰과 구조가 거의 같아서, 여기서 "복사 없이 재사용만으로 되는가"가 판가름 난다. 공지의 목록 즉시 노출 전환은 재사용 부품으로 바꾸고, 쿠폰·이벤트에는 없던 즉시 전환을 같은 방식으로 추가한다.
- **그다음** — 위키 관리 3종. 화면 파일 안에 복사돼 있는 입력 모달·확인 모달을 지우고 공용 부품으로 교체한다. 화면당 줄 수가 가장 크게 줄어드는 구간이다.
- **그다음** — 유저 관리(목록만 표준화, 상세는 아직 없음), 관리자 홈과 위키 관리 홈(메뉴 카드 통일 + **관리자 홈 주소 연결**).
- **마지막** — 커뮤니티 관리자. 깨진 참조(`useTableModal`)는 **없는 파일을 새로 만들어 복구하지 않는다.** 표준 입력 창 부품을 쓰면 그 훅 자체가 필요 없어지므로, 부품 교체로 문제를 소멸시킨다. 가짜 댓글 데이터는 실제 연동이 붙기 전까지 화면에서 뺀다. 그 전까지 커뮤니티 관리자는 지금처럼 주소 미연결로 둔다 — 켜면 즉시 오류가 나기 때문이다.
- **정리 대상** — 아무도 안 쓰는 중복 위키 화면 파일, 만들다 만 모바일/PC 분리 표 파일 세트는 해당 순서에 도달했을 때 삭제한다.

## 정해야 할 것

| 정할 것 | 선택지 | 권고 |
|---|---|---|
| 목록을 두 벌로 만들지, 한 부품이 변할지 | 두 벌 / 한 벌 | **한 벌.** 두 벌은 이미 고아 코드로 실패한 전례가 있다 |
| 여러 개 선택 일괄 처리를 이번에 만들지 | 지금 만듦 / 자리만 열어둠 / 안 함 | **자리만 열어둠.** 지금 어느 화면에도 없어 급하지 않고, 부품이 안정된 뒤 붙이는 게 안전하다 |
| 커뮤니티 관리자를 살릴지 폐기할지 | 부품으로 재작성 / 폐기 | **재작성하되 맨 마지막.** 다만 게시판·게시글·댓글·태그 4종이 실제로 다 필요한지는 **미확인** — 필요 없는 건 이때 함께 정리 |

## 나중에 할 것 — PC 화면 폭 지원 (지금은 하지 않음)

**지금 상태**: PC에서도 모바일과 똑같이 화면 가운데 좁은 폭(480px)으로 보이는 상태를 그대로 유지한다.
**아래 내용은**: 나중에 "PC에서는 화면을 넓게 쓰게 하자"고 결정할 때 그대로 꺼내 쓸 설계다.
**지금 작업에서는**: 아래 내용을 건드리지 않는다. 부품·화면 코드에도 반영하지 않는다.

### 모바일과 PC를 어떻게 다르게 보일 것인가

#### 갈림길 — 목록을 두 벌로 만들 것인가, 한 부품이 변할 것인가

| | 두 벌 (카드 부품 + 표 부품 따로) | **한 벌 (한 부품이 폭 따라 변형)** |
|---|---|---|
| 화면 파일이 하는 일 | 폭을 판단해 둘 중 하나를 고름 | 항목 정의만 넘김 |
| 항목 추가할 때 | 두 파일을 각각 고침 | 한 곳만 고침 |
| 각 폭에서의 완성도 | 각각 최적화 가능 (조금 유리) | 공통분모에 맞춰야 함 |
| 이 저장소에서의 전례 | **이미 시도했다가 아무도 안 쓰는 고아 코드로 남음** | 없음 (신규) |
| 개박살 위험 | 높음 — 한쪽만 고치면 즉시 어긋남 | 낮음 |
| 만드는 비용 | 부품 2개 | 부품 1개 (내부는 조금 복잡) |

**권고: 한 벌.** 근거 세 가지. (1) 두 벌은 이 저장소에서 이미 실패한 방식이다 — 만들다 만 채 방치된 모바일/PC 분리 파일이 증거다. (2) 관리자 목록은 항목이 4~10개로 적고, 모바일과 PC가 보여줘야 할 내용이 사실상 같다. 두 벌로 나눌 만큼의 정보 차이가 없다. (3) 관리자 화면이 앞으로 늘어날 때 화면 하나당 파일 두 개씩 늘어나는 구조를 피해야 한다.

#### 폭에 따른 배치 규칙

| 요소 | 좁을 때 (768px 미만) | 넓을 때 (768px 이상) |
|---|---|---|
| 목록 | 카드 세로 나열 | 가로세로 칸(표) |
| 검색·필터 | 검색창 한 줄 통으로, 아래에 필터 칩 가로 스크롤 | 한 줄에 검색창 + 칩 전부 |
| 등록 버튼 | 목록 위, 폭 전체 | 머리말 오른쪽 끝, 내용만큼 |
| 입력 폼 | 화면 가운데 뜨는 창 (폭 전체) | 오른쪽에서 밀려나오는 패널 (약 420px) |
| 폼 안 입력 항목 | 한 줄에 1개 | 한 줄에 2개 |
| 메뉴 카드 | 세로 1열 | 한 줄에 3열 |
| 화면 전체 폭 | 화면 꽉 채움 | 최대 1280px, 가운데 정렬 |

#### 어느 폭에서 바꿀 것인가

이미 정의된 다섯 단계(320 / 375 / 428 / 768 / 1024) 중 **관리자 화면에서는 768px 하나만 쓴다.**
- 428px(큰 폰)에서 바꿔봐야 여전히 카드가 맞다 — 표가 들어갈 폭이 아니다.
- 1024px에서 또 나누면 768~1023 구간을 위한 세 번째 모양이 생겨 부품이 복잡해진다. 표는 768px부터 이미 읽을 만하다.
- 320px 단계는 지금처럼 글자 크기 축소 용도로만 유지한다(기존 3곳 그대로).
- 여기에 "최대 1280px" 상한만 더한다. 이건 폭 단계가 아니라 상한값이므로 새 단계가 아니다.

#### PC에서만 제공할 기능

- **여러 개 선택해서 한번에 처리**(일괄 노출/숨김, 일괄 삭제)는 PC 전용으로 둔다. 모바일에 없어도 되는 이유: 일괄 정리는 앉아서 하는 대량 작업이고, 좁은 폭에서 작은 체크박스를 여러 개 누르면 오작동 위험이 크다. 무엇보다 **지금 어느 관리자 화면에도 이 기능이 없으므로 기능 후퇴가 아니다.**
- 다만 이번에 바로 만들지는 않는다. 목록 부품이 "왼쪽 선택 칸을 켤 수 있다"는 자리만 열어두고, 실제 일괄 처리 동작은 나중에 붙인다.

### 화면 폭 제한을 어떻게 풀 것인가

지금 480px 제한은 **네 군데**가 같은 값(`$layout-wrapper-max`) 하나를 공유한다 — 실측으로 확인했다.

| 어디 | 파일 | 무엇을 묶고 있나 |
|---|---|---|
| 페이지 전체 | `global/styles/base/_base.scss:36` | 문서 전체 폭 |
| 화면 틀 | `global/styles/mixins/_layout.scss:17` | 모든 화면의 공통 틀 |
| 상단 바 | `app/wrapper/mobile/parts/TopBar.module.scss:26` | 상단 바 폭 |
| 서랍 메뉴 | `app/wrapper/mobile/parts/Drawer.module.scss:25,26,55` | 서랍 폭 + **가운데 위치 계산까지 480 기준** |

여기에 더해, 개별 화면 스타일 파일에 480px을 **변수가 아니라 숫자로 직접 박아둔 곳**이 관리자 3곳(대시보드, 위키 관리 2종)과 위키 공개 화면 6곳에 있다.

| 방법 | 하는 일 | 공개 화면 위험 | 작업량 | 부작용 |
|---|---|---|---|---|
| **가. 제한 위치를 옮긴다 (권고)** | 페이지 전체의 480px 제한을 없애고, 폭 제한은 각 화면 틀이 진다. 공개 틀 = 480px 유지, 관리자 틀 = 1280px | **낮음** — 화면 틀에 이미 같은 480px 제한이 걸려 있어(주석에 "이중 안전망") 페이지 전체 쪽만 빼도 공개 화면 폭은 그대로다 | 중 (전역 파일 1곳 + 틀 1곳 + 관리자 틀 신규) | 상단바·서랍메뉴가 같은 480px 값에 묶여 있어 **함께 손대야 한다** (아래 확인 결과) |
| 나. 관리자 주소일 때만 제한을 푼다 | 페이지 전체 제한은 두고, 주소가 `/admin`이면 표시를 붙여 그때만 폭 제한을 해제 | 중 — 전역 상태를 주소마다 바꿈 | 소 | 화면 전환 순간 폭이 튀며 깜빡일 수 있음. "왜 여기만 다르지"가 코드에서 안 보임 |
| 다. 관리자를 아예 별도 앱으로 분리 | 관리자 전용 진입점을 따로 둔다 | 없음 (완전 격리) | 대 | 로그인·색상·부품을 두 벌 관리하게 됨 — 개박살 원인의 재생산 |
| 라. 480px 기둥 안에 두고 PC 지원 포기 | 아무것도 안 함 | 없음 | 없음 | 요구사항 미충족 (비교용) |

**권고: 가.** 페이지 전체의 폭 제한을 빼는 게 겉보기엔 가장 무서운 변경이지만, **화면 틀에 이미 똑같은 480px 제한이 걸려 있어서 실제로 공개 화면이 넓어지지 않는다.** 이 이중 안전망이 지금 상황에서는 오히려 안전한 이관 경로가 된다. 위험 관리는 두 가지로 한다.
- 개별 화면(관리자 대시보드, 위키 관리 여러 곳)에 따로 박아둔 480px 제한을 같은 작업에서 전부 걷어낸다. 안 걷으면 관리자 틀을 넓혀도 그 화면만 안 넓어진다.
- 상단 바와 서랍 메뉴도 **같은 480px 값을 공유한다** (실측 확인). 관리자 틀만 넓히면 본문은 넓어지는데 상단 바는 480px에 머물러 어긋난다. 특히 서랍 메뉴는 `left: 화면중앙 - 480px/2` 로 **위치 자체를 480 기준으로 계산**하고 있어서, 넓힌 화면에서는 엉뚱한 자리에 뜬다.
- 따라서 폭 값을 하나로 고정해 쓰지 말고, **공개용 폭과 관리자용 폭 두 개로 나눈 뒤 상단 바·서랍 메뉴가 지금 있는 구역의 폭을 따라가게** 만들어야 한다. 이건 선택이 아니라 필수 작업이다.
- 개별 화면에 숫자로 박아둔 480px(관리자 3곳, 위키 공개 6곳)도 같은 작업에서 정리한다. 공개 화면 쪽은 값을 공개용 폭 변수로 바꾸기만 하면 보이는 모습이 그대로다.

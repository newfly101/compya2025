## 2026-09-28 — 스토어 계층의 slices ↔ thunks 순환 참조 해소

- 버전: 유지 (refactor, 1.0.8 기준)
- 커밋: `a33ba6a7` (다른 도메인 store 정리와 공통 커밋, 이 문서는 authentication 부분만)

**고친 것**

- 로그인 상태 초기화(`clearUser`)를 thunk가 직접 디스패치하면서 `slices.js`와 `thunks.js`가 서로를 import하는 순환 참조가 있었다 — thunk는 응답만 반환하고 상태 반영은 공용 처리 함수(`applyAsyncHandlers`)가 맡도록 바꿔 순환을 끊었다. `clearUser`는 이제 `thunks.js`에서 타입 문자열(`"auth/clearUser"`)로만 디스패치된다. 인증 실패 시 화면이 비지 않도록 `initialized=true`를 세우는 동작은 그대로 유지됐다.

**손대지 말 것**

- `clearUser`를 다시 `thunks.js`에서 직접 import하지 말 것 — 그 순간 순환 참조가 되돌아온다.

**미결**

- 없음.

## 2026-09-28 — 동시 첫 로그인이 500 오류를 냈음

- 버전: 1.0.4 (patch)
- 커밋: `381e5761`

**고친 것**

- 같은 네이버 계정으로 두 요청이 거의 동시에 처음 로그인하면 DB 제약(같은 값 중복 방지) 충돌로 500이 났다. 경합에서 진 요청만 "이미 처리 중"(409) 오류로 안내하고, 진 쪽이 다시 로그인하면 정상 처리되도록 고쳤다.
- 처음 검토했던 "예외를 흡수하고 재조회" 방식은 채택하지 않았다 — 커밋 안 된 데이터가 남는 부작용(고아 회원)이 생기고, DB 격리 수준상 재조회도 실패하는 구조였다.

**손대지 말 것**

- OAuth `state`(위조 방지용 임시 값) 저장에 Redis 같은 새 저장소를 끌어오지 말 것 — 이미 쓰는 캐시로 충분하고, Redis 도입은 확정 일정이 아니다.

**미결**

## 2026-09-28 — 로그인 CSRF 방어가 이름만 있고 실제로는 동작하지 않았음

- 버전: 1.0.1 (patch)
- 커밋: `a3dc5dce`

**고친 것**

- 네이버 로그인 콜백이 위조 방지용 값(`state`)을 받기만 하고 아무것도 대조하지 않아, 공격자가 만든 로그인 링크를 피해자가 누르면 공격자 계정으로 로그인될 위험이 있었다.
- 서버가 직접 `state` 값을 만들어 5분짜리 쿠키에 담고, 콜백에서 쿠키 값과 요청 값을 대조하도록 고쳤다. 대조 직전에 쿠키를 먼저 만료시켜 한 번만 쓰이게 했다.

**손대지 말 것**

- 이 쿠키의 `SameSite=Lax` 설정을 `None`으로 바꾸지 말 것 — 네이버 콜백은 항상 "주소창 이동" 방식이라 `Lax`로도 쿠키가 정상 전달된다. `None`으로 바꾸면 로컬(HTTP) 환경에서 오히려 쿠키가 안 붙는다.
- OAuth `state` 쿠키를 공용 쿠키 생성 유틸(`AuthCookieFactory`) 밖에서 직접 만들지 말 것 — 로컬/운영 환경별 설정이 이미 그 유틸에 모여 있다.

**미결**

- 없음

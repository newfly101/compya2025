## 2026-09-28 — 관리자 회원 관리 표가 최근 20명만 보여주던 문제

- 버전: 1.0.1 (patch)
- 커밋: `eb84accc`

**고친 것**

- 관리자 회원 관리 화면이 운영 DB에 545명이 있는데도 서버 기본 페이지 크기(20)로만 조회해, 21번째 이후(오래된) 회원은 이름·이메일로 검색해도 "없음"으로 나오던 문제를 고쳤다. `users/store/admin/thunks.js`의 `requestAdminGetUserList` 기본값을 `{ page: 0, size: 1000 }`으로 바꿔, 요청이 나가는 지점 한 곳에서 전량(최대 1000명)을 받아오도록 했다. 운영 홈 배지가 회원 수를 20으로 표시하던 것도 같은 원인이었다(배지 쪽 수정은 `features/admin/history.md` 담당).

**손대지 말 것**

- 관리자 화면의 클라이언트 검색·정렬(`.filter`/`.sort`)을 "왜 서버에서 안 하지" 하며 걷어내지 말 것 — v2 핸드오프 스펙상 의도된 UI다. 문제는 정렬 방식이 아니라 조회 대상이 20명으로 잘려 있었다는 것뿐이었다.
- 닉네임 중복 검사를 새로 추가하지 말 것 — `service_nickname VARCHAR(20)`에 UNIQUE 제약이 없는 것은 "닉네임 중복 허용"이라는 문서화된 의도된 설계다. UNIQUE를 붙이면 기존 중복 행 때문에 DDL이 실패한다.
- `UserOAuthAccountEntity.ageRange`를 "안 쓰는 필드"라며 지우지 말 것 — "계속 수집(결정 유지) — 쓰는 화면 없음"이라고 코드에 명시된 의도적 미사용 데이터다.
- OAuth 스냅샷(이메일·프로필 이미지)이 재로그인해도 갱신되지 않는 것을 버그로 고치지 말 것 — 의도된 스냅샷 방식인지는 추정 단계라 확인 없이 "매번 최신화"로 바꾸면 안 된다.
- 프로필 수정 검증에 더 추가하지 말 것 — 이미 FE(trim+빈값거부+길이20)·서버(길이 재검사)·DDL(VARCHAR(20)) 3중이고, 프로필 이미지도 자체 업로드 URL만 허용하도록 이미 막혀 있다.
- `domain/oauth/**`가 개인정보를 로그에 남긴다고 보고 손대지 말 것 — TRACE 로그 호출 2건뿐이고 운영 로그 레벨이 전부 INFO라 실제로는 찍히지 않는다.

**미결**

- 탈퇴해도 개인정보가 안 지워짐 ⚠️ 법무 사안. 탈퇴 버튼은 계정 상태만 `WITHDRAWN`으로 바꿀 뿐 닉네임·이메일·프로필 이미지·OAuth 연동 정보가 전부 남는데, 개인정보처리방침은 "1개월 보관 후 파기, 복구 불가"를 약속한다. 파기 방식(행 삭제 vs 개인정보 칸만 비우기) 자체가 계정 PRD에서 "보류(사용자 결정)"로 이미 명시돼 있다 — 법무·기획 확인 필요. `policy` 도메인 이력에도 같은 문제가 문구 관점으로 기록돼 있다.
- 탈퇴 계정이 관리자 화면에서 상태를 "정상(ACTIVE)"으로 바꾸기만 하면 복구된다 — "복구 불가"라고 안내하는 처리방침과 정면으로 어긋난다. 관리자의 정상 업무(오인 정지 해제)를 막지 않으면서 정책을 정해야 하는 사안이라 위 파기 결정과 함께 묶어 정해야 한다.
- 탈퇴 회원이 관리자 회원 목록에서 걸러지지 않고 계속 보인다 — 위 두 결정과 같은 묶음에서 함께 정할 사안.
- 즉시 파기 요청을 처리할 관리자 기능(삭제 엔드포인트)이 아예 없음 ⚠️ 법무 사안 — 위 "탈퇴해도 개인정보 안 지워짐" 결정에 함께 걸려 있다. 지금은 운영자가 DB를 직접 만져 처리할 수밖에 없다.
- 죽은 코드 2곳(낮은 우선순위): 아무 화면도 쓰지 않는 `UserRow.jsx`(47줄), `AuthProvider.jsx`의 두 번째 `catch`가 절대 실행되지 않는 이중 체인 — 사용자 결정 불필요, 다음 라운드에서 정리하면 끝.

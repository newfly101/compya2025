# historyLegend

## 1. 무엇을 하는 기능인가

히스토리 모드 70라운드 × 25인 로스터를 조회하고, 그 안에서 레전드 카드 재료가 어디에 등장하는지를 "레전드별" 또는 "라운드별" 두 관점으로 탐색하는 조회 전용 화면이다. "레전드 재료"는 레전드 카드를 만드는 데 필요한 선수 카드 목록, "요일 정렬"은 표의 "요일" 열 헤더를 눌러 순서를 바꾸는 기능이다.

## 2. 화면과 진입 경로

| 화면 | 주소 | 어디서 들어오나 |
|---|---|---|
| 히스토리 재료 탐색기 (SC-14-01) | `/history-mode/legend` | 평점표(legendStats) 레전드 행의 딥링크(`?legend={레전드명}`), 브라우저 주소창 직접 진입 |

BE 패키지 이름은 `historyLegend`(FE 이름으로 통일, 커밋 `d000a940`), API 라우트는 `/api/history-rounds`, FE 폴더도 `domains/historyLegend` — 네 표기 모두 정상이다.

## 3. 규칙

| ID | 항목 | 규칙 | 근거 |

| REQ-HL-01 | 조회 | 비로그인 사용자가 히스토리 모드 70라운드×25인 로스터를 조회할 수 있다 | `GET /api/history-rounds` |
| REQ-HL-02 | 두 관점 탐색 | 레전드별/라운드별 두 관점으로 탐색할 수 있다. 라운드의 로스터 카드 중 레전드 재료 마스터와 매치되는 것만 "재료"로 집계한다 | `HistoryLegendScreen.jsx:441-506` |
| REQ-HL-03 | 필터·정렬·검색 | 필터(주차/일차/구단/타입/포지션)·검색(레전드명·구단명)·정렬(헤더 클릭)을 제공한다. 라운드 보기 기본은 일차 오름차순, 레전드 보기 기본은 재료 수 내림차순. 정렬 방향 라벨은 `day`/`days`만 "빠른순/늦은순", 나머지(`cnt`/`name`/`dow`)는 "많은순/적은순"으로 표시된다 — `name`(이름순)·`dow`(요일순)는 실제로는 순서 개념인데 라벨이 부정확하다(미구현, 고치기로 확정) | `config/historyLegend.js:155,167-172` |
| REQ-HL-04 | 로딩·에러 분리 | 라운드 요청과 레전드 메타 요청(다른 슬라이스, `legendStats` 도메인 공유)의 실패를 `metaError`로 분리해 내보낸다 — 라운드가 먼저 성공해도 메타 실패가 가려지지 않는다(2026-09-28 수정 완료) | `useHistoryLegend.js:11-13,24,59-61` |

## 5. 하지 않는 것

- 사용자가 뭔가를 입력·제출하지 않는다 — 순수 조회 전용 화면이다.
- historyLegend에서 다른 도메인으로 나가는 링크가 없다 — 평점표로 돌아가려면 브라우저 뒤로가기만 가능하다.
- 재료 데이터 유일성 검증은 코드가 아니라 운영 규칙으로 처리한다 — SQL로 재료 데이터를 직접 적재·수정한 뒤 검증 쿼리(`CREATE_01_data_history_mode.sql:138-142`, 주석 처리됨)를 돌려 확인한다.

## 6. 확인 필요

❓ 미정 — `position_code`(카드 포지션) 조사 완료 후 화면에 노출할 계획인지. 15행(0.86%)이 아직 비어 있다.

❓ 미정 — REQ-HL-03의 정렬 라벨 오분류(`name`/`dow`)를 고치는 작업이 아직 착수되지 않았다.

❓ 미정 — REQ-HL-05의 DB UNIQUE 제약 추가는 KST 통일 DDL 작업과 함께 예정이나 착수 시점이 정해지지 않았다.

확정(2026-09-30) — 캐시 만료(TTL)는 두지 않는다. 어드민 동기화 버튼이 캐시를 비우고 새로 채우며, 서버 재시작 시 최초 1회 다시 만들어지므로 충분하다.

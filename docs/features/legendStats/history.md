# legendStats — 변경 이력

## 2026-09-28 — 조회 전용 서비스 주석이 실제 동작과 달라 정정

- 버전: 유지 (주석만, 1.0.1 기준)
- 커밋: `d4dd5511` (legendStats·mileage·playerSkills·players 4개 도메인을 한 커밋에서 함께 정정. legendStats 변경 파일은 `FunLegendStatServiceImpl.java` 1개)

**고친 것**

- "SQL 로 값을 고치면 서버를 재시작해야 한다"던 클래스 주석이 거짓이었다. 실제로는 관리자 화면의 캐시 동기화 버튼을 누르면 `legendStat`·`legendPitchType` 두 캐시를 함께 비우고 다시 채운다. 이 거짓 주석을 근거로 과거 리뷰 문서가 "캐시 무효화 경로 없음"이라는 틀린 결론을 낸 적이 있어, 주석을 실제 동작으로 정정했다.

**손대지 말 것**

- 캐시 동기화는 자동이 아니라 관리자가 버튼을 직접 눌러야 하는 수동 갱신이다. 만료 시간(TTL)이 없어 그 버튼이 유일한 갱신 수단이라는 점도 그대로 유지.

**미결**

- 없음.

## 2026-09-28 — 평점 미정 인원 하드코딩 제거 + 재료 0건/실패 구분

- 버전: 1.0.1 (patch)
- 커밋: `6093d368`

**고친 것**

- 레전드 평점표 하단 안내문에 박혀 있던 고정 문구 "6명"을 없애고, 필터를 적용하지 않은 전체 74명 기준으로 미평점 인원수를 다시 계산해서 넣었다(`LegendStatsScreen.jsx:437`). 상단 안내문의 `unrated` 값(필터 적용 후 기준)을 그대로 재사용하지 않은 이유는 두 숫자의 의미가 다르기 때문이다.
- 레전드 카드 재료 목록이 안 보일 때 "정상적으로 0건 등록"과 "요청 실패"를 구분하지 않고 같은 실패 문구를 띄우던 것을 고쳤다. `useLegendStats.js`에 응답을 정상적으로 받았는지 나타내는 `hasMaterialsResponse` 값을 추가해, 로딩중 / 재료없음 / 불러오기실패 3단계로 나눴다.

**손대지 말 것**

- 복합 포지션(예: "RF/1B") 레전드 7명은 BE `splitPositions()`가 `position_code`를 슬래시로 쪼개 배열로 응답하고 FE가 `includes()`로 포함 검색하는 정상 동작이다 — 결함이 아니다. DB 실측(`position_code` NULL 0건, 74명 중 복합 7명)으로도 확인됐다.
- `pitchAverage()`가 항상 `null`을 반환하는 것은 아직 수집 대상이 아닌 값이라는 의도된 상태다(코드 주석에 명시).
- v1 화면 폐기로 죽은 `getAll()`/`getMaterials()` 컨트롤러는 삭제 여부가 사용자 결정 사안이라 이번 라운드에서 손대지 않았다.

**미결**

- 실제 미평점 인원수가 정확히 몇 명인지, 재료 8행이 74명 전원 완비됐는지는 DB 접속 금지로 미확인 — 코드는 몇 건이 오든 정확히 동작하므로 기능 자체에는 영향 없음. DB 접속 가능한 세션에서 실측 필요.
- `loaded` 재요청 차단(캐시 동기화 후에도 열린 탭이 재조회 안 함)을 legendStats도 매 진입 재조회로 바꿀지는 성능 트레이드오프라 도메인별 판단이 필요하다.

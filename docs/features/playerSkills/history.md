## 2026-09-28 — 재요청 방지 조건을 items.length 대신 명시적 플래그로

- 버전: 유지 (refactor, 1.0.0 기준)
- 커밋: `a33ba6a7` (여러 도메인 store 정리 공통 커밋, 이 문서는 playerSkills 부분만)

**고친 것**

- `usePlayerSkills.js`의 재요청 방지 조건이 "받은 개수가 0인지"(`items.length === 0`)로 판단하고 있어, 성공했지만 0건인 응답을 받아도 매번 다시 요청했다 — 슬라이스에 `loaded` 플래그를 두고 `fulfilled`에서 세우도록 바꿔 "한 번이라도 받았다"와 "0건"을 구분했다. 재요청 가드는 이제 `!loaded && !loading`이다. 실데이터(타자·투수 각 46개)에서는 기존과 결과가 같고, "성공했는데 0건"인 경우만 동작이 달라진다(재요청하지 않음 — 의도한 수정).

**손대지 말 것**

- 이전 기록(`d4dd5511`)의 "`loaded` 대체 가드(`items.length===0`)는 정상 설계" 메모는 이 수정 **이전** 상태를 가리킨다 — 지금은 명시적 `loaded` 플래그로 바뀌었으니 그 메모를 근거로 되돌리지 말 것.

**미결**

- 없음.

## 2026-09-28 — 조회 전용 서비스 주석이 실제 동작과 달라 정정

- 버전: 유지 (주석만, 코드 동작 불변)
- 커밋: `d4dd5511` (playerSkills·players·legendStat·mileage 4개 도메인을 한 커밋에서 함께 정정. playerSkills 변경 파일은 `PlayerSkillServiceImpl.java` 1개)

**고친 것**

- "캐시를 비우는 경로가 없어 SQL로 값을 고치면 서버를 재시작해야 한다"던 클래스 주석이 거짓이었다. 실제로는 어드민 화면의 캐시 동기화 버튼을 누르면 재시작 없이 `playerSkill` 캐시가 비워지고 다시 채워진다 — 다만 자동이 아니라 관리자가 버튼을 직접 눌러야 한다. 이 거짓 주석을 근거로 과거 리뷰 문서 4편이 "캐시 무효화 경로 없음 = 무관"이라는 틀린 결론을 낸 적이 있어 정정했다.

**손대지 말 것**

- `loaded` 대체 가드(`items.length === 0`)는 재요청 차단 구조로 정상 설계다.
- `SKILLS_LIST`의 광고 자리(10번째 항목 뒤부터 노출)는 과거 반려 대응으로 넣은 의도된 가드다.
- `PlayerSkillMapper.xml`의 정렬(`ORDER BY sort_order DESC, tier, value_order`)은 FE가 다시 정렬해 화면 영향은 없지만, 캐시에 올라가는 값을 안정적으로 만드는 목적이 있어 제거하지 말 것.
- DDL(테이블 설계)과 실제 DB 데이터의 불일치는 실측 결과 0건이었다(`data_player_skill` 92행, 스킬×티어 540행 전부 DDL 기대치와 일치) — "DDL이 실데이터와 어긋난다"는 예전 우려는 근거 없음.

**미결**

- `adapter.js`의 원 안 숫자(`CIRCLED`) 5개 지원 vs `skillsUtils.js` 정규식은 3개까지만 그룹으로 인식 — 시드 데이터의 실제 최대 그룹 크기가 3이라 지금은 증상 없음. 고치는 방향이 두 갈래(정규식 확장 vs 배열 축소)라 스킬 그룹 크기 4개 이상이 추가될 때 결정.
- 캐시 만료 시간(TTL) 없음 — 운영 설정(`spring.cache.type`) 변경은 별도 승인 사안.

## 2. 순서의 이유

| 결정 | 이유 |
|---|---|
| 결함 수정(1)을 이관(3~4)보다 먼저 | 새 코드에 옛 결함을 옮겨 심지 않는다. 그리고 수정 효과를 **현행 사이트에서** 바로 확인할 수 있다 — 이관과 결함 수정이 섞이면 회귀 원인을 가를 수 없다 |
| 저장소 구조(2)를 Next 생성(3) 직전에 | 폴더 이동은 diff 가 크고 기능 변화가 없다. 다른 변경과 섞지 않고 한 PR 로 끝낸다 |
| 정적 페이지 → 목록 → 상세 → 상호작용 순 | 위험이 작은 것부터. 정책 페이지 4개로 레이아웃 · 메타 · 배포 경로를 먼저 검증한다 |
| SEO(5)를 컷오버(6) 직전에 따로 | "화면이 같다" 와 "검색엔진이 보는 것이 같다" 는 다른 검사다. 기준선(0) 과 비교해 통과해야 컷오버 |
| 서버 런타임(7)은 선택 | 정적 export 로 목표(크롤러가 본문을 받음)가 달성된다. 인프라 추가는 콘텐츠가 요구할 때 |

---

## 3. 병행 규칙

- 0~5단계 동안 운영은 **`web/` 이 계속 담당**한다. 운영 버그 수정은 `web/` 에 하고, 이관된 페이지가 있으면 `frontend/` 에도 같은 수정을 한다(PR 체크리스트 항목).
- 새 기능 개발은 4단계에서 해당 도메인이 이관된 뒤 `frontend/` 에만 한다. 이관 전 도메인의 새 기능은 가능하면 미룬다.
- 단계마다 **단계 PR 하나 + 결함별 PR 여러 개**. 단계 PR 은 이 폴더의 체크리스트 갱신만 담는다.

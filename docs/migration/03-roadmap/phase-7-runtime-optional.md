# 7단계 (선택) — 서버 런타임: SSR / ISR

> 목표: 정적 export 로 부족해졌을 때만, 서버 렌더를 **필요한 경로에만** 추가한다
> 닫는 결함: [BE-04](../02-diagnosis/backend/BE-04-cookie-model.md)(서버 인증 부분)
> 운영 영향: 인프라 추가

---

## 1. 진입 조건 — 둘 이상 참일 때

[`01-background/rendering-options.md`](../01-background/rendering-options.md) §4 와 같다.

- 커뮤니티 글쓰기가 열려 사용자 글이 분 단위로 늘어난다
- 공지 재빌드 대기(수 분)가 운영상 문제가 된다
- 로그인 사용자별 화면이 색인 대상이 된다
- 정적 페이지 수 때문에 빌드가 10분을 넘는다

---

## 2. 배치 선택지

| 선택 | 구성 | 장점 | 비용 · 위험 |
|---|---|---|---|
| A. 기존 EC2 에 Next standalone | `output: 'standalone'` + systemd, nginx 가 HTML 요청을 Next 로 프록시. 정적 자산은 S3 + CloudFront 유지 | 새 서비스 계정 없음. BE 와 같은 배포 방식(SSM) 재사용 | BE 와 같은 인스턴스 자원 공유 — 메모리 여유 확인 필요. 장애 격리 약함 |
| B. 관리형 플랫폼(Vercel · Amplify 등) | Git 연동 배포 | ISR · 미리보기 배포가 기본 | 월 비용, 도메인 · 쿠키 도메인 설계 재검토 |
| C. 경로 혼합 | 대부분 정적 export 유지, 커뮤니티만 서버 | 영향 범위 최소 | 두 배포 방식 공존 — 1인 운영 부담 |

권장 순서: **A 로 시작**(추가 비용 없음, 배포 방식 동일) → 부하나 격리 문제가 보이면 B.

---

## 3. 바뀌는 것

| 영역 | 변경 |
|---|---|
| 렌더링 | 커뮤니티 목록 · 글 상세를 `revalidate` 또는 요청 시 렌더. 나머지는 SSG 유지 |
| 갱신 | 5단계의 재빌드 트리거 → BE 가 Next 의 on-demand revalidation 엔드포인트(`revalidateTag`)를 호출. 비밀 토큰으로 보호 |
| 인증 | BE-04 선택지 A(서버에서 인증 안 함) 우선. 개인화 서버 렌더가 필요하면 B(쿠키 전달) + refresh 쿠키 path 확장 |
| 스토어 | 요청마다 `makeStore()` — 3단계에서 이미 준비됨 |
| 보안 | 서버 fetch 에 사용자 쿠키를 전달하는 코드는 **공개 캐시 대상 응답에 절대 섞지 않는다**(캐시 오염 · 정보 노출) |
| 운영 | Next 프로세스 헬스체크, 로그, 메모리 알람 추가 |

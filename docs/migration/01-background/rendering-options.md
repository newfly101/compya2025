# 렌더링 방식 비교와 선택

> 기준일: 2026-09-25
> 대상 독자: "왜 SSR 이 아니라 정적 export 부터인가" 를 설명해야 하는 사람

---

## 1. 용어 — 한 표로

| 방식 | HTML 을 언제 · 어디서 만드나 | 크롤러가 받는 것 | 인프라 | 이 프로젝트의 예 |
|---|---|---|---|---|
| **CSR** | 요청 후, 브라우저에서 | 빈 `div` | 정적 호스팅 | v1 ~ 2026-08-30 |
| **prerender(스냅샷)** | 빌드 때, 헤드리스 브라우저에서 | 스냅샷 HTML (hydrate 안 함) | 정적 호스팅 | 현재 |
| **SSG** | 빌드 때, Node 에서 React 렌더 | 완성 HTML, 브라우저가 hydrate | 정적 호스팅 | 이관 1차 목표 |
| **SSR** | 요청마다, 서버에서 | 완성 HTML, hydrate | Node 서버 상시 운영 | 7단계 후보 |
| **ISR** | 빌드 때 + 정해진 주기/요청 시 다시 | 완성 HTML, hydrate | Node 서버 또는 플랫폼 | 7단계 후보 |

핵심 차이 두 가지:

1. **hydrate 여부** — SSG/SSR 은 서버가 만든 DOM 을 React 가 **이어받는다**. prerender 스냅샷은 React 가 모르는 DOM 이라 버리고 다시 그린다.
2. **어디서 실행되나** — SSG/SSR 의 데이터 조회는 Node 에서 일어나 CORS 가 없다. prerender 는 브라우저에서 일어나 CORS 가 걸린다.

## 2. 선택지 비교 (2026-09 기준 판단)

| 선택지 | 얻는 것 | 치르는 값 | 판단 |
|---|---|---|---|
| A. prerender 계속 보강 | 코드 수정 최소 | FE-01~04 가 구조적으로 남음. 대기 로직 땜질이 계속됨 | 단기 유지, 장기 탈출 |
| B. Vite SSR 직접 구성 | 번들러 유지 | 라우팅 · 데이터 로딩 · 메타 · hydrate 를 직접 설계. 1인 유지보수 부담 | 기각 |
| C. React Router v7 framework mode | 기존 라우터 개념 재사용, 프리렌더 지원 | 라우트 파일 구조 전환 필요, 생태계 · 채용시장 자료가 Next 대비 적음 | 차선 |
| D. Astro | 정적 콘텐츠에 최적, JS 최소 | 어드민 · 로그인 · 탐색기처럼 상호작용이 많은 화면은 React 섬(island)으로 쪼개야 함 | 기각 (상호작용 비중 큼) |
| **E. Next.js App Router** | 메타 · 정적 경로 · 404 · sitemap 이 프레임워크 기능. 정적 export → 서버 런타임으로 **점진 전환 가능** | 서버/클라이언트 컴포넌트 경계 학습, 브라우저 API 정리 | **채택** |

E 를 고른 결정적 이유는 **같은 코드베이스로 정적 export(1차)와 SSR/ISR(7단계)을 모두 갈 수 있다**는 점이다. 인프라를 바꾸는 결정을 콘텐츠가 요구할 때까지 미룰 수 있다.

## 3. 1차를 정적 export 로 하는 이유

| 근거 | 설명 |
|---|---|
| 공개 페이지가 전부 인증 없이 그려진다 | 정책상 조회 화면은 전부 공개 → 빌드 때 모두 만들 수 있다 |
| 콘텐츠 변경 빈도가 낮다 | 게임 데이터는 SQL 시드로 수동 적재, 공지 · 쿠폰 · 이벤트는 하루 몇 건 수준. 지금도 재빌드로 운영 중이다 |
| 인프라를 그대로 쓴다 | S3 + CloudFront + GitHub Actions 유지. Node 서버를 새로 운영하지 않는다 |
| 인증 재설계를 미룰 수 있다 | 로그인 화면은 클라이언트 컴포넌트로 두고 지금의 쿠키 방식(API 도메인)을 그대로 쓴다 |

정적 export 에서 **못 하는 것**과 대응:

| 못 하는 것 | 영향 | 대응 |
|---|---|---|
| ISR · 요청 시 렌더 | 새 공지는 재빌드 전까지 상세 HTML 이 없음 | 어드민 공지 발행 → 배포 워크플로 트리거(5단계). 그 사이 상세는 클라이언트 렌더로 보여 줌 |
| middleware · 서버에서 쿠키 읽기 | 서버 측 로그인 가드 불가 | 가드는 클라이언트 유지(지금과 동일). 관리자 API 는 BE 가 이미 막고 있다 |
| `next/image` 최적화 | 이미지 자동 변환 불가 | `images.unoptimized: true`, 카드 이미지는 기존 `build:cards` 로 미리 생성 |
| rewrites / redirects | 주소 이전 처리 | CloudFront Function 에서 처리(지금처럼) |

## 4. 언제 SSR/ISR 로 넘어가나 (7단계 판단 기준)

아래 중 **둘 이상**이 참이 되면 서버 런타임을 검토한다.

- 커뮤니티 글쓰기를 열어 사용자 글이 분 단위로 늘어난다
- 공지 발행 후 재빌드 대기(수 분)가 운영상 문제가 된다
- 로그인 사용자별 화면(내 기록 · 추천)이 색인 대상이 된다
- 빌드 시간이 정적 페이지 수 때문에 10분을 넘는다

넘어갈 때 치를 값은 [BE-04](../02-diagnosis/backend/BE-04-cookie-model.md)(쿠키 모델)와 [`phase-7-runtime-optional.md`](../03-roadmap/phase-7-runtime-optional.md) 에 적어 둔다.

## 2. CSR 이 왜 반려 사유를 만들었나

CSR(Client-Side Rendering)은 서버가 **빈 HTML 과 JS 번들**만 주고, 브라우저가 JS 를 실행해 화면을 그리는 방식이다.

```
[브라우저/크롤러] --GET /skills--> [S3]
                <-- index.html (본문: <div id="root"></div>) --
                --GET main.js--> 실행 --GET api/player-skills--> 렌더
```

| 관찰자 | 무엇을 보나 | 결과 |
|---|---|---|
| 사용자 | JS 실행 후 완성된 화면 | 문제없음 (느린 첫 화면 정도) |
| JS 를 실행하지 않거나 늦게 실행하는 크롤러 | 빈 `div` | "본문 없음" |
| 애드센스 자동광고 | 본문이 그려지기 전의 빈 화면에 광고 삽입 | 반려 사유 ① 을 **우리가 직접 만듦** |
| 검색 색인 | 모든 주소가 같은 HTML · 같은 title · 같은 canonical | 페이지가 서로 구분되지 않음 → 사유 ② 로 이어짐 |

구글 크롤러는 JS 를 실행할 수 있지만, **렌더링 큐가 따로 있어 늦고 보장되지 않는다.** 애드센스 심사는 "사람이 읽을 본문이 HTML 에 있는가" 를 본다. 그래서 "크롤러가 알아서 JS 를 돌려 주겠지" 는 이미 한 번 반려된 가정이다.

## 3. 반려 사유별로 구조가 한 일

| 반려 사유 | CSR 구조에서의 원인 | 임시 해법(현재) | 근본 해법(이관 후) |
|---|---|---|---|
| ① 콘텐츠 없는 화면의 광고 | 자동광고가 렌더 전 빈 화면에 붙음 | 자동광고 끄고 수동 슬롯 + `ADS_ENABLED` 게이트 | 본문이 이미 HTML 에 있음. 슬롯은 hydrate 뒤에만 채움 |
| ② 가치 없는 콘텐츠 | 모든 주소가 같은 빈 HTML · 같은 메타 | prerender 스냅샷 + 가이드 글 + 공시 상세 noindex | 페이지별 HTML · `generateMetadata` · 실제 404 |
| (숨은 원인) 크롤러가 못 따라감 | 링크가 `onClick` 이라 `href` 가 없음 | `<a href>` 로 교체(8곳) | Next `<Link>` 가 기본적으로 `<a href>` 를 렌더 |

## 4. 정리

- 반려는 콘텐츠 양만의 문제가 아니라 **HTML 에 콘텐츠가 없는 구조**의 문제였다.
- prerender 는 이 구조를 바꾸지 않고 **빌드 때 브라우저를 한 번 돌려 결과를 찍어 두는** 방식이다. 효과는 있었지만 한계도 구조에서 온다 → [`prerender-stopgap.md`](./prerender-stopgap.md).
- 콘텐츠 가치(확률 공시 해설 · 커뮤니티 글쓰기)는 렌더링과 별개로 남은 과제다. 이관으로 해결되지 않는다 — Notion 「서비스 정책」 6장.
